# Changelog

Release notes of omp-cloud, newest first. `mise run release -- <version>` moves `## Unreleased` into a dated section, and the release workflow publishes that section as the GitHub release's notes. Write each entry for someone who runs the service.

## Unreleased

- **Read-only threads.** The new setting and thread policy key `policy.readOnly` (default `false`) makes a cloud agent that only reports: its result is never pushed, asked about or opened as a pull request (the `push` event says `not pushed: the thread is read-only`), its VM gets no `mcp.json` and no MCP proxy token (a `vm` event says `MCP servers not delivered: the thread is read-only (<names>)`), and its system prompt tells it to change nothing. A thread may turn it on and never off, and the service's own setting makes every thread read-only. An `Idempotency-Key` is now bound to `policy.readOnly` as well as the prompt, so a replay never hands back a writable thread for a read-only request (a key stored before this release replays as a request without it). See `docs/api.md` and `docs/security.md`.
- **Agents the model starts run as subagents.** A thread with `origin: "tool"` now runs with omp's `ask` tool off and a subagent system prompt: its assignment is the message that started it, it works autonomously, and its final message is its result. The prompt also names the parent to message with `write agent://<id>`, lists the names of the secret environment variables, and tells the agent to start a dev server detached and name its port. An agent that needs a decision ends its turn with the question as its result and its parent answers by messaging it. Tool and push approvals still reach you. Threads you start with `/cloud <task>` are unchanged.
- **A model's delegation starts blank and says which agent it started.** The `cloud` tool no longer forks the conversation into an agent unless the call passes `conversation: "full"` (your own `/cloud <task>` still does). `delegate` answers ``task N: agent `<Name>` (thread <id>) started`` with the agent's id, the conversation and MCP servers that shipped (`mcp servers:`), and a `next:` line; a finished turn arrives as a `<task-result id="<Name>" agent="cloud" status="…">` envelope like a `task` subagent's, with the reply inline up to 5000 characters and a preview beyond it, and a cloud agent's reply is escaped so it cannot close the envelope or forge a notice. A plugin against a service without `threads.subagent` warns that its agents may ask questions.
- **Model fallback and login hints.** When the session's model is not one the cloud serves and the model named none, the tool's `delegate` runs the cloud's default model and says so in `warnings`. A named model the cloud does not serve is `invalid` (`this cloud does not serve <model>`, with the served ids in the hint), and a cloud with no model login is `not_configured` (`this cloud has no model login yet`), with a hint that tells the model to ask you to log the server in, `/cloud login <provider>` or, from a paired device, `omp-cloud login <provider>` on the server machine. `/cloud <task>` keeps its login offer.
- **A session picks its cloud.** `/cloud use [env | personal | paired]` and the tool's `use` choose among the clouds this machine knows (`OMP_CLOUD_URL`, the `url` and `token` of `config.yml`, the pairing); the choice is stored in the session as an `omp-cloud-target` entry and is refused once the session has launched or adopted a thread. `/cloud status` and `info` show `cloud:` and `other clouds:` lines when there is more than one. `/cloud connect` now switches a session that has no threads to the new pairing and says `new sessions use … first` when a `url` is configured. The tool's `connect` pairs a server you name after you confirm a `Connect to omp-cloud?` dialog; it never replaces a pairing and never passes `--allow-public`. The `cloud` tool has 17 ops.
- **ssh pairing judges a host name by where it points.** `/cloud connect user@host` and the tool's `connect` no longer need `--allow-public` for a name outside `.local`, `.lan`, `.home.arpa` and `.internal` when every address it resolves to while pairing is local, such as a name in your own domain that points at the server's LAN address. A name that resolves to a public address and a public IP address are still refused without the flag, and a pairing code's names are still judged by their text, since whoever wrote the code chose both its addresses and its fingerprint.
- **`/cloud connect` shows what it is doing.** While it pairs, a line above the editor names the step (asking the server for a device over ssh, checking the server's certificate, checking the service with the new device token) until the result card replaces it; before, nothing showed until the card.
- **Plan mode delegates read-only agents.** While omp is in plan mode every delegation the model makes sets `policy.readOnly`, whatever it passes (against a service without `threads.readonly` it fails with `version_skew` before uploading anything), and the model's `pull` and its messages to agents that are not read-only, through `send` or `write agent://<id>`, are refused. A read-only thread stays read-only, so a delegation repeated with the same `ref` after plan mode is a `conflict`. `preview`, `diff`, `files`, `use`, `connect`, `stop` and `delete` still work, and your own `/cloud` commands are not restricted.
- **`info` says what a cloud agent gets.** The tool's `info` now lists the default model and whether the session's model is served, what agents may do (`agents may: fetch · web search · browser · egress`), the toolchain (`vm.packages`), what happens to their work (`git.push`, pull requests, signing, push credentials) and `plan mode: on` when it applies; a failing `info` still lists the clouds the model can `use`. A device token may read `GET /api/v1/settings` for this; only writing is the owner's. The tool's description and `docs/cloud-tool.md` now say what a cloud agent has and what happens to its work.
- **Focusing a cloud agent in the Agent Hub works, and its row shows its cost.** Opening a running cloud agent's detail in omp's Agent Hub (Tern's included) failed with `this.ctx.viewSession.agent.getPendingToolResults is not a function`, and the next members omp reads when it attaches the transcript, the status line and the timers it schedules would have failed the same way; a focused cloud agent now answers all of them as a session with no local tools, retries, compaction, queue or todos, shows its conversation and run state, and the status line shows its model, context and cost. The hub's row (and the status line's cost total) showed `$0.0000` for an agent whose first turn was still running while the job tile showed its real cost, because the thread's metrics sum finished turns only and the hub reads cost from the agent's session ahead of the job's progress; the session now adds the running turn's requests, tokens and cost, so the row, the total and the tile agree.
- **Prompts and replies are formatted on a thread's dashboard page.** The Turns card showed each turn's prompt and reply as raw Markdown, with `#`, `**`, `-`, `|` and backticks on screen. It now renders them: headings, bold, italics, strikethrough, inline code and code blocks, ordered, nested and task lists, tables (wide ones scroll sideways), block quotes and rules. A **Formatted / Raw** switch on the card shows the text exactly as written instead, for every turn on the page; the browser remembers the choice. The text is never inserted as HTML, only `http` and `https` links are clickable, and an image is shown as a link to it and never loaded, so a reply cannot make the dashboard fetch anything. The page still shows the first 2000 bytes of a prompt, so a long one can end mid-list or mid-table; it is shown as far as it goes. The release notes window uses the same renderer and looks as before.
- **Service API 5.** `whoami` reports `api: 5` and the capabilities `threads.readonly` (the `policy.readOnly` key) and `threads.subagent` (the `ask`-less subagent threads). There is no database migration.

## 0.6.1 (2026-10-22)

- **A secret the cloud agent printed no longer reaches a pull request.** omp hides secret values from the model but prints the real value to you, so a reply could contain one, and the pull request's description quotes the reply. Before a pull request is opened or updated, the service now replaces every secret value it delivered to the thread (its own `secretEnv` and secret files, and the Secrets that match its repository) with `[secret <NAME>]` (`[secret file <path>]` for a secret file) in the description's omp-cloud section and in the title. Env values under 4 characters are left alone, as in masking. The reply on the service, the dashboard and your omp is unchanged. If the thread's secrets cannot be read, the pull request is not opened or updated and a `pr` event says `pull request not updated: could not read the thread's secrets: <reason>`; the push is unaffected.
- **Cloud agents no longer receive or return memory.** Every handoff shipped your whole local omp memory store, all projects included, into the VM, where the agent and anything it read or ran could read it, and what the cloud agent retained was merged into the store your local omp recalls from. Both directions are gone. omp in the VM now runs with `memory.backend: off` (set in the service's config, which wins over the `config.yml` and overlays you ship), the plugin ships no `~/.omp/agent/memories` and keeps the `memory`, `mnemopi` and `hindsight` settings out of the shipped `config.yml` and overlays, and `/cloud pull`, `/cloud resume` and a followed thread merge nothing: your local omp keeps its own memory untouched, and what it learns from a cloud result is what it retains itself. The service drops what only the export used: `GET /api/v1/threads/{id}/memory`, the create request's `memory` field (an older client's is ignored like any unknown field), the threads' `memoryBank`, `whoami.vmWorkspace` and the capability `threads.memory`. The release adds a database migration that drops the `memory_bank` column (`omp-cloud backup` first, as migrations are forward-only). The VM template no longer installs `sqlite3`, which only the export needed, so its tag changes: the first thread after the update waits once for the template to rebuild, and a VM that already exists keeps working from the old one.

## 0.6.0 (2026-10-22)

- **GitHub, set up once from the dashboard.** The dashboard has a GitHub page. Connect creates a private GitHub App on your account (or an organization you name) through GitHub's manifest flow, and "Install on repositories" lets you choose which repositories it reaches. From then on `github.com` counts as a host the service holds a credential for: fetches and pushes use a one-hour installation token for that one repository, handoffs from github.com repositories ship only what GitHub lacks, and `github.com` needs no `git.hosts` entry. The token never enters a VM. On a repository the App is not installed on, a `github.com` entry in `git.hosts` is still used; without one the fetch or push says `the GitHub App <slug> is not installed on <owner>/<repo>` and links the install page. The App has Contents, Pull requests and Metadata permissions and no Workflows permission, so a push that changes `.github/workflows/*` is refused by GitHub, on purpose. The App's private key is `<dataDir>/github/app.pem` (0600). See `docs/github.md`.
- **Verified commits.** Make a signing key on the GitHub page, add its public key to GitHub as a Signing Key, and set `git.sign` to `ssh` (default `off`). After each turn the service re-signs that turn's commits with its own Ed25519 SSH key, using the App owner's noreply address as committer, and the VM adopts the signed tip, so the next turn, the stored result, `/cloud pull` and the push all carry the same signed commits. Only the turn's new commits are rewritten: commits an earlier turn already exposed keep their ids, so switching signing on later is safe. A failure leaves the unsigned result in place with a `notice` event. An App owned by an organization has no noreply address: set `git.committer` (`Name <email>`) to one verified on the account that holds the key. After a push the thread's events say whether GitHub shows the head as Verified. The key is `<dataDir>/signing/ed25519.pem` (0600).
- **Pull requests.** After a push to a github.com repository the App is installed on, the service opens a draft pull request into the branch you handed off from and keeps an omp-cloud section of its body (the latest reply and `/cloud pull <id>`) current on every later push; what you wrote outside the section stays. `git.pr` is `draft` (default), `ready` or `off`. A pull request you close without merging is not reopened, and a failure never changes whether the push happened. The thread's `pr` field, the turn card (`PR #<n> <url>`), the dashboard's thread page and the `cloud` tool's `status` show it. Needs `git.push` `ask` or `auto`.
- **Signed handoff commit.** When your repository signs commits (`commit.gpgsign`), the commit that carries your uncommitted work at handoff is signed with your key too. A hardware key or pinentry prompt that takes more than 30 seconds falls back to an unsigned commit with the launch warning `the handoff commit is unsigned: <reason>`.
- **`/cloud <task>` offers the missing login.** When the model's provider is one the cloud has no login for, and you are on the server machine in omp's interactive UI, omp asks whether to log the cloud in now instead of refusing; yes runs the same sign-in as `/cloud login <provider>` and hands the task off.
- **Service API 4.** `whoami` reports `api: 4`, the capabilities `github.app`, `commits.signed` and `threads.pr`, and `github: {app, signing}`; threads carry `pr`. New owner-only routes: `GET`/`DELETE /api/v1/github`, `POST /api/v1/github/manifest` and `/conversions`, `GET /api/v1/signing`, `POST`/`DELETE /api/v1/signing/key`. New settings `git.sign`, `git.committer` and `git.pr`. The release adds a database migration (the pull request columns).
- **Backups** now include `github/` and `signing/` when they exist, so a restore brings the App and the signing key back. They hold private keys: keep the archives as protected as the data directory.
- **Secrets, set once on the service.** The dashboard has a Secrets page (and `PUT /api/v1/secrets/{name}` takes the owner token): an environment variable with a literal value or a `!command` that prints it, and the repositories whose threads receive it, as globs such as `github.com/acme/*`. The repositories are required and never implied; `*` means every thread. A thread's VM gets the matching secrets, merged under its own `secretEnv`, in an env file omp is started under, and omp's secret obfuscation is turned on so the values are masked in what is sent to the model. A change reaches a thread when its VM is next provisioned. Values are never served; the thread gets a `notice` when a `!command` fails, and a `vm` event lists the names. Literal values are stored in the database as text, like `update.token`: keep your backups protected.
- **MCP servers go with the handoff.** The servers of `~/.omp/agent/mcp.json` ship with `/cloud <task>`: an http server through a new MCP proxy on the service, which adds the server's headers (and its OAuth token, below) so no MCP credential enters the VM, and a stdio server run in the VM with its `env` written as `${NAME}` references to your Secrets. The launch card has an `mcp` row; a server that cannot ship (SSE, a loopback URL, a header that does not resolve, literal values in a stdio `env`) stays home with a warning that says why. The proxy refuses an upstream that is or resolves to the service host (loopback, link-local, the gateway), and allows LAN addresses for servers in your homelab. `omp-cloud setup` adds `"mcp": {"listen": "10.254.254.1:4100"}` to `service.json` on a rerun, so rerun it and restart the service after updating; without the section, or when the address cannot be bound, the service runs without the proxy and http servers are not delivered.
- **MCP logins.** `/cloud login mcp:<https url>` or `omp-cloud login mcp:<https url>` logs the service in to an MCP server's OAuth (discovery and dynamic client registration included) and keeps the token in its database, refreshed on use. Only the owner token, on the server machine, does it.
- **Settings that stay on your machine.** A handoff no longer ships your omp's credentials, host paths and `!command` settings (the `auth.broker` subtree, API tokens, `shellPath`, `mnemopi.dbPath`, any value starting with `!`, endpoints that point at localhost, and the rest of the list in `docs/secrets-and-mcp.md`) in `config.yml` and the `--config` overlays; the launch card warns `<file>: <key> stays on this machine` for each. `cloud` and `extensions` leave silently.
- **Service API, more.** `whoami` also reports the capabilities `secrets.store` and `mcp.proxy`, `mcpProxy` and `mcpLogins`; thread creation takes an `mcp` array. New owner-only routes: `GET /api/v1/secrets` and `PUT`/`DELETE /api/v1/secrets/{name}`. The release adds a database migration (the secrets, MCP login and per-thread MCP tables); `omp-cloud backup` carries them with the rest of the database.
- **The cloud agent shares your Mnemopi memory.** The memory you ship with a handoff is now findable: when your omp uses Mnemopi's per-project banks (`memory.backend` `mnemopi`, `mnemopi.scoping` `per-project` or `per-project-tagged`, no `mnemopi.dbPath`), the plugin renames your project's bank to the name omp derives for the VM's working directory (`/home/user/work`), so the cloud agent's recall sees what you retained. Your own store is not touched.
- **What the cloud agent remembers comes back.** After every turn the service snapshots the VM's Mnemopi databases (`VACUUM INTO`, a consistent copy while omp is running) into `memory.tar`, replacing the last one. When you follow a thread, `/cloud pull` it or `/cloud resume` it, your plugin merges the new working memories (created after the thread began, not already in your store by id or content) and their annotations into your default store and the project bank, and omp embeds them the next time it opens the store. The archive is treated as untrusted input: a fixed list of members, the database attached with `trusted_schema` off, only the columns your database has; the VM's file is never copied into place, a database you lack is created with the schema of one you have, and when you have none the merge waits (`☁ the cloud memories of <id> are not merged yet: <reason>`) until your omp makes one. A failed merge is a warning, `☁ could not merge the cloud memories of <id>: <reason>`, and never fails the pull. Only new rows merge: edits and deletions in the VM, other banks and embeddings do not come back, and a custom `mnemopi.dbPath` or another memory backend is left alone. Cloud memories enter your local recall, so read "Cloud memories" in `docs/security.md`; how it works is in `docs/commands.md` (Memory).
- **VM template gains `sqlite3`.** The template recipe changed, so its tag changes: the first thread after the update waits once for the template to rebuild. A VM that was already running from the old template keeps working and exports no memory until it is replaced.
- **Service API, memory.** `whoami` reports the capability `threads.memory` and `vmWorkspace`; a create request takes `memory: {bank}` and threads carry `memoryBank`. New route: `GET /api/v1/threads/{id}/memory` serves the export (`application/x-tar`, `404` `no memory yet`). A failed export is a `notice` event, `the memory could not be saved: <reason>` (the reason is the last line `sqlite3` or `tar` printed), never a failed turn; a VM with no memory or no `sqlite3` exports nothing and says nothing, and no `sqlite3` error is mistaken for either, whatever exit code its version uses. The release adds a database migration (the memory bank column).
- **The VM toolchain is a setting, and the default one is bigger.** The new settings `vm.packages` (the Debian packages of the VM template) and `vm.setup` (shell lines run as root when the template is built) are edited on the dashboard's Settings page. The default `vm.packages` is `build-essential`, `python3`, `python3-venv`, `python3-pip`, `nodejs`, `npm`, `unzip` and `ripgrep`, so a cloud agent starts with a toolchain, and a stdio MCP server that needs node or python has its runtime. Any change, the default included, gives the template a new tag: the first thread after the update waits once for the rebuild, VMs that already exist keep their template, and `omp-cloud doctor` checks the template of the recipe you have stored. A package that does not exist, or a failing line, fails the build and the threads that need it until you fix the setting. See `docs/environments.md`.
- **Repository environments.** A repository's `.omp-cloud.yml` takes a `setup: {run, cacheFiles}` script (in the repository's file only; your personal file ignores it with a warning). The service runs it once in a throwaway VM and keeps the disk as a vibemon snapshot, so the next thread on that repository starts with its dependencies installed instead of installing them again. The cache key is the template, the repository, the script and the contents of `cacheFiles` (default: `bun.lock`, `bun.lockb`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `Cargo.lock`, `go.sum`, `poetry.lock`, `uv.lock`, `requirements.txt`, `Gemfile.lock`, `composer.lock`), so a changed lockfile builds a new one. Only a thread's first VM builds; a restore starts from a cached environment or the plain template, and a failed setup never blocks the thread (`environment setup failed: exit <code>: …`, then the template). The build runs in a sandbox of its own (`app` `omp-cloud-env`, killed by the lifecycle sweep when a service that died leaves one past 2 hours), with the repository's Secrets in its environment, the thread's egress and a 30 minute limit. At most 20 environments are kept (those of an old template first, then the least recently used). Restoring a repository now runs `git clean -fdq`, which removes untracked files a snapshot left and keeps ignored ones, so dependencies live in ignored directories. The launch card has an `env setup` row. A snapshot keeps whatever the script wrote to disk, a secret included: see `docs/security.md`.
- **Previews.** `/cloud preview <id> <port>` opens a web server the cloud agent runs in its VM in your browser, and `/cloud preview stop` ends it. The service relays the requests to the VM's port through vibemon, resuming a paused VM and postponing its idle pause while you look at it; the plugin serves them at `http://localhost:<a free local port>/` on your machine and refuses any other host name (including `127.0.0.1`), so the previewed page never shares the dashboard's session cookie, which the forwarder also strips. Websockets are not forwarded. The route takes bearer tokens only, and the dashboard listener answers `404` for it.
- **Service API, environments and previews.** `whoami` reports the capabilities `threads.setup` and `threads.preview`; a create request takes `setup: {run, cacheFiles?}` and the thread detail carries `setup`. New route: any method on `/api/v1/threads/{id}/ports/{port}[/<path>]` (`400` for a bad port or 49983, `409` without a VM, `501` for a websocket upgrade, `502` when vibemon does not answer). New settings `vm.packages` and `vm.setup`, and `vm` events for the environment steps. The release adds a database migration (the thread's setup columns and the `environments` table); the snapshots themselves live in vibemon and are not in `omp-cloud backup`.
- **Docker in a VM.** A VM can run Docker: add `docker.io` to `vm.packages` and `usermod -aG docker user` to `vm.setup`. Debian starts the daemon itself, and `docker run hello-world` works as the VM's user without `sudo` (see [Configuration](docs/configuration.md#docker)).
- **A resumed thread no longer hangs after another thread's VM was deleted.** vibemon gives a paused VM's address up, so another thread's VM could take it and, when that thread was deleted, leave a connection behind on the host that answered the resumed VM's old connection to the model or the gateway with nothing: its next turn waited until the turn timeout. A resume of a paused VM now drops all of its connections (a `vm` event, `dropped the connections the paused VM held from <addresses>`), so the agent opens fresh ones.
- **The model can preview too.** The `cloud` tool has a 15th op, `preview`: `{op: "preview", thread, port}` opens a port of a cloud agent's VM at `http://localhost:<lp>/` and returns the address, so the model can open it with omp's browser tool and screenshot, click through or read what the agent built; `{op: "preview", stop: true}` (optionally with `thread` and `port`) ends previews. It shares the forwarders of `/cloud preview`: a call reuses one you started, and `/cloud preview stop`, `/cloud disconnect` and ending omp end the model's too. The op asks for approval like `send` and needs the capability `threads.preview`.
- **Release notes are formatted in the dashboard.** The "What's new" window (header) and the Settings card's "Release notes" window rendered the notes as raw Markdown, with `**`, backticks and `-` run together. They now show bullets, bold titles, `code`, emphasis, headings and links; only `http` and `https` links are clickable, and the notes are never inserted as HTML.

## 0.5.3 (2026-10-22)

- **A login that never took effect.** Running a second `omp-cloud serve` on the service host (for example `omp-cloud` with no command, which serves by default) replaced the running service's own gateway client before it failed on the taken port. From then on the service could not read which models the gateway serves, so after a successful `omp-cloud login` the cloud still said it could not run the provider until the service was restarted. A second `serve` now claims the API address first and stops at once with `… is already in use: the omp-cloud service is probably already running`, changing nothing. While it starts, the API answers `503 the service is starting`.
- **The service recovers its gateway client by itself.** When the gateway stops accepting the service's client, the service issues a new one and reads the model list again within seconds, keeping the last list meanwhile. Before, it kept the rejected client until a restart.
- **Logging in from a paired device.** A paired device can't log the cloud in to a provider (that takes the owner token, which stays on the server), but the plugin still told it to run `/cloud login`, which then failed with `only the owner token can do this`. On a paired device, the handoff refusal, `/cloud login`, the hub, `/cloud status` and the `cloud` tool now name the server and the command that works there: `omp-cloud login <provider>` on the server, for example over `ssh -t`. `/cloud login` on a paired device stops before contacting the service.

## 0.5.1 (2026-10-21)

- **Cloud agents.** `/cloud <task>` hands your repository (uncommitted changes included) and the conversation to an omp agent in its own KVM microVM on your hardware, running the same omp you run. It works on its own branch and asks you questions when it needs to. After 10 minutes idle (`runner.idleTimeoutSeconds`) its VM pauses with its processes intact, and the next message resumes it. A lost VM is replaced from the last result and conversation. `/cloud pull <id>` fetches `omp-cloud/<id>` and saves the cloud conversation as a local omp session, and `/cloud resume <id>` continues it locally.
- **The `/cloud` plugin.** The command set is `/cloud` (the hub), `[new] <task>`, `list`, `show`, `watch`, `unwatch`, `send`, `answer`, `stop`, `pull`, `resume`, `delete`, `login`, `update`, `dashboard`, `pair`, `connect`, `devices`, `disconnect`, `status` and `help`. A thread is named by its id, a unique suffix or prefix, a word of its name, or the job id omp shows for it. A message that starts with `/` runs in the cloud agent's own omp (`/usage`, `/compact`, extension commands, and so on); see `docs/commands.md`.
- **The `cloud` tool.** omp's model drives cloud agents through one tool with 14 ops (`delegate`, `list`, `status`, `read`, `events`, `diff`, `files`, `send`, `answer`, `stop`, `wait`, `pull`, `delete`, `info`). `delegate` starts one thread or up to 8 from one snapshot, and a repeated `ref` replays the first thread instead of creating another. Work that needs no repository runs as a scratch thread in an empty repository. Errors carry a code and say whether the outcome is known; see `docs/cloud-tool.md`.
- **Cloud agents are omp jobs and agents.** A running cloud turn shows in omp's Subagents strip, the jobs pill, `/jobs`, Tern's Background jobs panel and `wait`, and as `proc://<id>`, with step dots, per-turn bars, a context meter, cost, tokens and a live output tail. `agent://<id>` reads the latest reply and `history://<id>` the conversation. For a thread the model started, the finished turn arrives as omp's own async-result, and cancelling the job in omp stops the cloud turn. `omp stats` counts the cloud's spend with yours; see `docs/jobs.md`.
- **Messaging and drill-in.** `write agent://<id>` messages a cloud agent with omp's own semantics and answers with a receipt: `injected` into the running turn at its next step, `woken` for an idle agent, `revived` for an archived one. A message carries an id, so a retry is safe. A cloud agent writes back to `agent://Parent`, and the message reaches your omp as an ordinary incoming message.
- **Live events and child jobs.** A running turn writes `usage`, `tool_start` and `tool_end` events before it ends, and the background jobs and subagents a cloud agent starts in its VM write `child_start`, `child_progress` and `child_end` events. They appear under the agent's job in omp's jobs panel and `/jobs`. A child still open when the VM is paused, lost or released ends `cancelled` with the reason.
- **Questions and approvals.** An agent's `ask` questions come back as cards that list their options (a click on one answers it in Tern) and open omp's own ask dialog for a thread you started. Finished turns and questions go to a cloud inbox (the footer count and the `/cloud` hub) and to the terminal's attention tray, so they cost the model nothing; `deliver: transcript` in `~/.config/omp-cloud/config.yml` posts cards instead. Tool approvals, `prompt` rules and the push question always go to you, and the `cloud` tool refuses to answer them.
- **Native in Tern.** Cards, the `/cloud` hub and the `cloud` tool's results draw as Tern's own nodes; in a terminal without Tern's protocol they are framed with omp's own output block and status line.
- **Git and push policy.** The service fetches bases, composes bundles and pushes results from its own git cache; git credentials and the push never go into a VM, which holds only its gateway client token. `git.push` is `never` (default), `ask` or `auto`, and it never forces and never writes a protected branch (`git.protected`, default `main`, `master`, `develop`, `release/*`) or the remote's default branch. For a remote whose host the service holds a credential for, the handoff ships only what the remote lacks.
- **Agent policy and spend caps.** Bash rules (`policy.bash.patterns`), per-tool approvals, `policy.fetch`, `policy.webSearch`, `policy.browser`, an egress allow-list (`policy.egress`), allowed models and spend caps per turn, thread and day (`policy.spend.*`, in USD). A thread can tighten the service's policy and never loosen it.
- **Archive.** A thread nobody touches for `lifecycle.archiveAfterDays` (default 7, 0 never) has its VM released; its conversation and work are kept, and the next message restores it. Orphaned sandboxes and gateway clients are swept.
- **The dashboard.** `/cloud dashboard` prints a one-time sign-in link to a loopback web page styled after omp's `/stats`, in a light and a dark theme: Overview, Threads by repository (with an Archived filter), a thread page with context use, cost and tokens per turn, Spend, VMs, Devices, Logins and Settings. Run-time settings are typed, apply without a restart, are audited and can be exported as YAML.
- **Pairing.** Other machines pair once, from a code (`/cloud pair`, then `/cloud connect`) or over ssh (`/cloud connect user@host`), and get their own revocable device token over a TLS connection pinned to the service host's certificate. The owner token is refused on the remote listener, which accepts private source addresses by default. `/cloud devices revoke` ends a device immediately.
- **One-command install.** `curl -fsSL https://raw.githubusercontent.com/TechDufus/omp-cloud/main/install.sh | sh` downloads the release binary, checks its sha256 and runs `omp-cloud setup`. Setup prints a plan and asks first, uses sudo once for the root work, and then sets up vibemon (pinned per release), the persistent system and user units (they survive a reboot), the `omp-cloud` vibemon team (32 concurrent sandboxes by default), the service config and TLS identity, the plugin and the model login. It is idempotent and never changes firewall rules. It needs a Linux x86_64 host with `/dev/kvm`, systemd and omp 18.12.3 or newer.
- **`omp-cloud` commands.** One binary with `setup`, `doctor`, `login`, `uninstall`, `serve` (the default), `ssh-pair`, `update`, `install`, `backup` and `version`. `doctor` checks the machine and the whole stack, including that your omp loads the plugin, prints the fix beside each failure and exits 1 on a failure. `login [<provider>]` logs the service in to a model provider and prints the URL in full. `uninstall [--purge]` removes what setup installed and keeps your backups. A daily timer runs `backup`: one archive of the database, blobs and git cache.
- **Updates.** The service checks the release feed hourly (`update.mode`: `off`, `notify` by default, `auto`), downloads and verifies a newer release, and installs it on one click in the dashboard, with `/cloud update` or with `omp-cloud update apply`. The update waits up to 60 s for the new version to answer `/api/v1/health`, rolls back if it does not, and restores the pre-update backup when the release changed the database schema. `auto` installs by itself only when no thread has been starting, working or waiting for 10 minutes and the release needs the same vibemon and database schema. omp shows `update ready` in the cloud footer and the hub, and the plugin is refreshed with the update; see `docs/updating.md`.
- **Service API 3.** `GET /api/v1/whoami` reports the service version, `api: 3`, the capabilities (including `threads.irc`, `events.live` and `events.children`), limits, spend and models, so a client checks for a feature before it uses it; a plugin that needs one the service lacks says so (`version_skew`). The contract is in `docs/api.md`.
- **Releases and license.** Each tagged version is published on GitHub Releases as one `omp-cloud` executable per architecture (linux x86_64 and arm64; `install.sh` and setup accept only x86_64) with a `release.json` manifest, sha256 sidecars and a `THIRD-PARTY-NOTICES.txt` that lists every bundled package with its license; `omp-cloud version` prints the version and build id. omp-cloud is MIT-licensed (`LICENSE`; the plugin carries its own copy in `plugin/LICENSE`).
- **Known limitations.** See `docs/architecture.md`, "Known limitations".
