# Pairing

[README](../README.md) · [Documentation index](../README.md#documentation)

Other machines use the cloud without the owner token: each one pairs once and holds its own device token, which you can revoke. A device must have the plugin installed first (`omp plugin marketplace add TechDufus/omp-cloud`, then `omp plugin install omp-cloud@omp-cloud`, then `/restart`; [Other machines](install.md#other-machines)), because `/cloud connect` is a plugin command. `omp-cloud setup` creates the TLS identity (`~/.config/omp-cloud/tls/`: a self-signed P-256 key, `0600` in a `0700` directory, and its certificate, valid for 100 years, generated by setup itself with no `openssl`) and the `remote` section of `service.json` once; it never overwrites either. On an existing `service.json` it adds a missing `remote` section. The listeners are defined in [API](api.md#listeners); the limits on offers, codes and attempts are in [Devices and pairing](api.md#devices-and-pairing).

## Add a device

1. On the service host, in omp's interactive UI: `/cloud pair`. It shows the code as text with a countdown (it works once and expires after a few minutes), and sends it to your clipboard once (through the terminal's clipboard escape sequence, so over SSH or Tern remote it can land on the machine you type on). Nothing confirms the copy and some terminals ignore the sequence (tmux by default, VTE terminals): if pasting fails, copy the code from the overlay by hand. Esc closes the overlay and cancels the code. The dashboard's **Devices** page shows the code with a Copy button.
2. On the other machine, in omp: `/cloud connect` and paste the code (or `/cloud connect <code> [--name <name>]`). The device is named after the machine unless `--name` gives a name of 1 to 64 letters, digits, spaces, `.`, `_` or `-`. A machine that is already connected refuses until `--replace`, which pairs again and revokes the old device. There is no QR code: the other machine is a computer running omp, and nothing in the flow scans one.
3. The device reads the certificate of the remote listener and goes on only if its fingerprint equals the one inside the code. It then asks to pair, and the service host shows `name · platform · address` with the keys `y approve with full access · t approve with threads-only access · n decline · esc cancel` (the dashboard has Approve and Decline). The approval says what access the device gets, `threads` (threads and reads only) or `full` (everything the owner token can do): see [Access levels](#access-levels). An approval that names none, which is what a client without access levels sends, gives `threads`. The device waits, with a countdown, and only after approval does it receive its token, once. When it is paired, the card on the device ends with `access: full access` or `access: threads only — a connection with full access can change that`.
4. The device keeps the pinned certificate and its token in `~/.config/omp-cloud/connection.json` (`0600`; `$XDG_CONFIG_HOME`, `%APPDATA%` on Windows, where file modes do not apply). An `OMP_CLOUD_URL` or a `url` in `config.yml` wins over it as the default (`/cloud use paired --default` makes the pairing the default: it writes `use: paired` to `config.yml`); `/cloud status` says which connection is in use. A session can pick the pairing anyway: `/cloud use paired`, or `/cloud connect`, which switches a session that has no cloud threads to the new pairing. The pick is stored in the session as an `omp-cloud-target` entry, so it survives a restart of omp and applies to that session only. A machine still holds one pairing.

## Over SSH

If you can ssh to the service host's account, skip the code: `/cloud connect user@host` (also `host` or `ssh://user@host:2222`) asks the service host's own `omp-cloud ssh-pair` to create the device, and there is nothing to approve, because being able to log in to the service's account is the proof that you own it; the device has full access. ssh runs without a password prompt, so key-based login and a known host key are needed (it tells you what to run: `ssh user@host` once to accept the host key, `ssh-copy-id`). The certificate fingerprint arrives over ssh, and nothing is sent to an address until the certificate there matches it; the device then writes `connection.json` as above. Until the card appears, a line above the editor names the step it is on (asking the server for a device, checking the server's certificate, checking the service with the new device token). `OMP_CLOUD_SSH` names another ssh program (a file name, no arguments). The service host needs the `omp-cloud` command, installed by `omp-cloud setup` (`mise run infra:up` in a checkout), and the service must have run once on that account (the command never migrates the database, and says to restart the service or `git pull` when its schema differs from the one this `omp-cloud` expects). If `omp-cloud` is not found there, the error says to install it there and run `omp-cloud setup`; the [agent prompt for a remote service host](agent-setup.md) does both ends.

The model can pair too, when you ask it to: the `cloud` tool's `connect` takes the same targets (`user@host`, `host`, `ssh://…` or a pairing code) after you confirm the `Connect to omp-cloud?` dialog. It never replaces an existing pairing (that stays `/cloud connect --replace`) and never passes `--allow-public`.

## Manage devices

`/cloud devices` (or the dashboard) lists them with each one's access (`<name> · full access · …` or `<name> · threads only · …`, the device you are on marked `(this device)`) and when and from where each was last seen; `/cloud devices revoke <name|id-prefix>` revokes one after a confirmation. Revoking is immediate: its next request gets 401, and its open event streams and in-flight requests end. Threads it started keep running; the command lists them. `/cloud disconnect` revokes this machine's device and deletes `connection.json` (`--force` deletes the file even when the service cannot be reached, and the token then stays valid until you revoke it on the service host).

On a paired device, `/cloud dashboard` starts a loopback forwarder (`127.0.0.1`, random port, one-time sign-in link) that relays the dashboard and its API to the service over the pinned connection. Every device can do what the owner does with threads (launch, send, answer, stop, pull, delete). A device with `threads` access sees only its own entry in the device list and cannot create or approve pairings, change settings, run provider logins or MCP logins, read or change the service's secrets, mint dashboard links, change devices' access, revoke other devices or check for and install updates; a device with `full` access can do all of those ([API](api.md#devices-and-pairing)). The owner can change a device's access at any time (`PATCH /api/v1/devices/{id}`). When the cloud has no login for a provider, a device without full access is told to log the server in on the server machine: `omp-cloud login <provider>`, over ssh as `ssh -t <user>@<host> '~/.local/bin/omp-cloud login <provider>'` (`/cloud login` is refused on a device without a request).

## Access levels

A device has `full` access (everything the owner token can do) or `threads` access (its own threads, and reads). You choose when you approve it: `y` for full, `t` for threads-only, or no choice from a client that predates access levels, which gives threads-only. A device paired over ssh has full access.

`/cloud devices access <name|id-prefix> full|threads` changes it later, from a connection with full access: the owner token on the server machine, or a device that has full access. It answers `☁ <name> now has full access` or `☁ <name> now has threads-only access`, and the change takes effect on the device's next request. Lowering the device you are on asks first, `This device loses full access now`, because that connection can no longer raise it again. A device with threads-only access that runs it gets the service's refusal, `this device has threads-only access; a connection with full access can change that`. Against a service without access levels the command says to update the service.

`/cloud pair` needs full access too. On a device with threads-only access it says `/cloud pair needs full access; this device (<name>) has threads-only access`; a device with full access can pair others.
The dashboard on a paired device shows the device's name with a `full access` or `threads only` badge in the header (the owner's own session shows `Owner`), and the cloud's name beside the brand. With `full` access its **Devices** page has a Full / Threads only switch per device, and a pending request there offers **Approve with full access**, **Approve, threads only** and **Decline**; giving the device you are using `threads` access asks first and reloads the page. With `threads` access Logins' start form, GitHub and Secrets show `Needs full access`, Settings is read-only and the update pill has no button.

## What crosses the network

TLS to the remote listener, which serves the self-signed certificate; the device pins its fingerprint and trusts no certificate authority, so a different certificate at the same address is refused before anything is sent. The device token travels only in the `Authorization` header over that TLS connection. The owner token never does (the remote listener rejects it), and neither do provider or git credentials. The pairing code holds a one-time secret the service stores only as a hash, and device tokens are stored hashed (SHA-256) in the database; the plaintext exists only in each device's `connection.json`. The unauthenticated pairing routes answer every failure alike and rate-limit wrong attempts ([API](api.md#devices-and-pairing)).

## Who may connect

The remote listener accepts only private source addresses by default and always refuses the gateway address; `remote.allow` replaces the list of sources and `remote.advertise` sets the addresses a code names (default list and settings: [configuration](configuration.md#service-config)). `/cloud connect` refuses an address that is not local unless `--allow-public`; loopback, private and link-local addresses are local. A name in a pairing code counts as local only by its text (one label, or ending `.local`, `.lan`, `.home.arpa` or `.internal`), because whoever wrote the code chose both its addresses and its fingerprint. Over ssh, where the fingerprint comes through your own login, a name counts as local when every address it resolves to while pairing is local, so `me@nas.example.com` pairs without the flag on a network where that name points at the server's private address. `connection.json` keeps the name, and later connections look it up again without this check ([Known limitations](architecture.md#known-limitations)).

The `cloud` tool's `connect` applies the same rule and never allows a public address: for one, run `/cloud connect --allow-public` yourself. It asks for your confirmation before it pairs anything ([Security model](security.md#pairing-by-the-model)).

## Firewall

Allow TCP 8443 from your LAN to the service host, for example `sudo ufw allow from 192.168.0.0/16 to any port 8443 proto tcp`. Setup never changes firewall rules.

## Backups and identity

A device is a database row, so restoring an older backup brings back devices you revoked after it was taken: revoke them again. The TLS identity lives with the service config, not in the backup archive. If `tls/` is replaced or lost (`omp-cloud uninstall --purge` removes it), every device's pin stops matching and each must pair again.
