# Security model

[README](../README.md) · [Documentation index](../README.md#documentation)

What the service, the VMs and your devices can reach, what runs as root, and what crosses between your omp and a cloud agent.

## Trust boundaries

- The service has three listeners, defined in [API](api.md#listeners): the API listener (`listen`, plain HTTP, loopback only) for the owner token and this machine's devices, the dashboard listener (`dashboard.listen`, plain HTTP, loopback only) for the dashboard's session cookie, and the remote listener (`remote`, TLS, set up on `0.0.0.0:8443`) for paired devices only. The owner token is refused on the remote listener; the dashboard listener's `POST /session` accepts it to open a session.
- **Access levels.** A paired device is the owner on its machine and has one of two access levels ([API](api.md#tokens-and-callers)). `full` is everything the owner token can do: settings, provider logins, the GitHub App and signing key, secrets, pairing offers and approvals, other devices' access and revocation, and installing updates. `threads` is threads, reads and its own revocation. The owner decides at approval; the approval defaults to `threads` when it names none, so an old client never grants more than it meant to. A device paired over ssh has `full` access, because a login on the service's account already is ownership. A device with full access can approve new full devices and change any device's access, so treat it like the owner token: revoke it to take its power back. The gate is one function, `requireScope`, checked before any route runs; a route that needs full access and is missing from it is open to threads-only devices, so a new route of that kind is added there with a test. A change of access applies to the device's next request, and a `403` body names the fix.
- The remote listener is the only omp-cloud listener reachable from other machines. vibemon and the auth broker listen on loopback, and the gateway and the [MCP proxy](#secrets-and-mcp) on `10.254.254.1`. The service is the only vibemon client.
- **The vibemon admin token leaves root as a 0600 file.** `omp-cloud setup` copies `VMON_ADMIN_TOKEN` from `/etc/vmon/env` (root-only) to `~/.config/omp-cloud/vmon-admin.token` (0600), and `vmon.adminTokenFile` names it, so the service can read the cluster's capacity (`/admin/cluster`, `/admin/teams`). The token is never in a step's text, the `--json` report or a log. Anything that runs as the owner can read that file and so act as vibemon's admin: create and delete teams, mint API keys, change limits. The service itself uses it only for those two read-only routes and sends it only to `vmon.url`.
- **Other vibemon machines.** A server that takes them (`omp-cloud setup --cluster-address`, [More vibemon machines](install.md#more-vibemon-machines)) binds vmon's cluster and gossip listeners (TCP 7947, TCP and UDP 7946) to its one LAN address, never `0.0.0.0`: every VM reaches all ports of the service address (`10.254.254.1`), so an all-address listener would be open to VMs. The ports are protected by the cluster secret, not by TLS: put them on a network you trust, and never on the internet (setup refuses a public address). The cluster secret leaves root only in cluster mode, as `~/.config/omp-cloud/vmon-cluster.secret` (0600), so that `omp-cloud node-join-info` can hand it to a machine that joins over ssh; anyone who runs as the owner can read it, and it is in no step text, `--json` report or log. A server that takes no other machines never copies it.
- **A node's VMs reach only the gateway.** A VM on a node reaches `10.254.254.1` through its machine's vmon, which dials from the node's host, so the traffic arrives at the server from the node's LAN address, which the remote listener and every other all-address listener would accept. The node's unit `omp-cloud-node-net` therefore rejects everything its host sends or forwards to `10.254.254.1` except TCP 4000 (the gateway) and TCP 4100 (the MCP proxy), in the OUTPUT and FORWARD chains. The rules are inserted at the head of both chains, so a blanket `ACCEPT` that another firewall tool added earlier cannot precede them. The node's `vmon` unit has `Requires=omp-cloud-node-net.service` with `After=` rather than the `Wants=` the design first named: with `Wants=`, systemd starts vmon even when the node-net unit failed (the iptables call failed at boot, say) and a later stop or restart of that unit leaves vmon running, so VMs would run without the restriction; with `Requires=`, vmon does not start when the unit fails and stops or restarts with it. The unit is a oneshot that stays active after its rules are gone, so `omp-cloud doctor` on a node also tries the restriction: an unprivileged `curl` to `10.254.254.1:8443` must be refused, and it fails the check when it connects. The server's remote listener (8443) is still reachable by the node's host itself under its real LAN address, which is what the sync timer uses, pinned to the server's certificate.
- A VM holds one per-thread gateway client token. Provider credentials and git credentials never enter it. What else reaches it is what you scope to it: the service's [secrets](#secrets-and-mcp) whose `repos` match the thread's repository, the thread's own `secretEnv` and `secretFiles`, and the entries of its stdio MCP servers.
- The cloud broker has its own OAuth login (`/cloud login <provider>`); yours is never copied.
- **What a threads-only device may read about logins.** `GET /api/v1/logins` ([API](api.md#the-login-list)) answers every caller with the cloud's provider names, login and renewal dates and the cause of a disabled login, and the MCP server hosts; the account (email, account id, organization) shows only with full access. It carries no token material: the service reads the broker with its own bearer token and copies only identity and date fields. The unauthenticated `GET /api/v1/health` also carries the vibemon tag installed on the service host (`vmon`), like the omp-cloud version it already shows.
- VM egress: the internet, plus the gateway IP. vibemon runs with `--egress-internal-allow 10.254.254.1/32`, so every other private range is denied. That exemption covers every port of the address, and a VM's traffic reaches the service host from it, so a host listener bound to all addresses is reachable from VMs; the remote listener refuses that source. `policy.egress` narrows the internet to a list for new VMs.
- `bash.patterns` (and the fixed git guard in the VM) is a guard, not a boundary: its globs see the command text with quotes removed and over-match, and `g=git; $g pus"h"` evades them. The boundaries are the missing credentials, the push policy (a [read-only thread](#read-only-agents-and-plan-mode) is never pushed) and egress.
- What an agent writes is untrusted, and the dashboard shows it on the origin that holds the owner's session cookie. A turn's prompt and reply (and the release notes) are rendered as a Markdown subset built from React elements: no HTML from the text is ever inserted, so it cannot run script; only absolute `http` and `https` links become anchors (new tab, `rel="noreferrer"`); and an image is shown as a link to its URL and never loaded, so a reply cannot make your browser fetch a tracking or exfiltration URL by being displayed. A link is still a link: check where it goes before you open it.

## What runs as root

- **Setup.** `omp-cloud setup` runs as your user and calls `sudo` once, for one command (`omp-cloud setup system …`): packages, the vibemon install, two system units and the helper below. It refuses to run as root, and the sudo password prompt is yours: setup never supplies or caches it. `omp-cloud uninstall` does the same in reverse. Setup never changes firewall rules.
- **The helper and its sudoers rule.** `/usr/local/libexec/omp-cloud/vmon-install` is root-owned (0755) and is the only thing `/etc/sudoers.d/omp-cloud` (0440, checked with `visudo -cf`) lets your user run without a password. The rule never covers the `omp-cloud` binary, which your user owns and can replace. The helper takes one argument, a vibemon tag, and downloads, verifies and installs only that release ([Updating](updating.md#vibemon-is-pinned)); the updater uses it so a one-click update that moves vibemon needs no password.
- **System units.** `omp-cloud-net` (the dummy `ompsvc0` link at `10.254.254.1`, the only address sandboxes reach on the host) and `vmon` (vibemon) are system services; the omp-cloud service, the auth broker, the gateway and the backup timer are your user's units and never run as root. A node ([More vibemon machines](install.md#more-vibemon-machines)) has `vmon` in the node role, `omp-cloud-node-net` and a timer, `omp-cloud-vmon-sync`, that runs the root script `/usr/local/libexec/omp-cloud/vmon-sync`. The script reads only `SERVER_URL` and `SERVER_PIN` from `/etc/omp-cloud/node.env` (line by line, validated, never sourced), asks the server's pinned `GET /api/v1/health` for its vibemon tag (`curl -q`, answers over 64 KiB refused, so no curlrc of root applies) and runs the root helper with that tag: it can only move vibemon to a release the server runs, and the helper refuses a downgrade. A certificate that is not the pinned one is reported as a failure of the unit (exit 1, nothing installed), not as an unreachable server. It first probes the helper's install lock and does nothing while another install holds it, so a manual run never makes the sync record a failed tag. `omp-cloud setup node` runs one `sudo` like setup does, and the cluster secret reaches the root part only as a path to a 0600 file in a private temp directory that is removed afterwards; the root part accepts only a secret of letters, digits and `. _ ~ + / = : -` (what an `EnvironmentFile` carries byte for byte), a private LAN address for `--cluster-address`, and a plain dotted-quad address that is no `0.0.0.0`, loopback, multicast or broadcast for `--server`.
- **Linger.** Setup runs `loginctl enable-linger` for your user so those user units start at boot without a login, records that in `/etc/omp-cloud/setup.json`, and `uninstall` undoes only what setup enabled (`--no-linger` skips it).

## Messages between your omp and a cloud agent

A cloud agent can be messaged from your omp and can message it back, the way omp's own agents message each other ([Messaging a cloud agent](jobs.md#messaging-a-cloud-agent); the endpoint is [IRC messages](api.md#irc-messages)). This adds a channel across the trust boundary above. What matters for trust:

- **The VM extension.** `irc-peer.ts` runs in each VM's omp with the VM agent's own privileges, inside the VM's limits (the gateway-only egress above, no git or provider credentials). Its only host import is omp's `registry/agent-registry`; apart from `node:` built-ins it imports nothing and opens no sockets. An outgoing message leaves as a status frame on omp's stdout, which the runner already reads.
- **Inbound (you to the agent).** A message reaches a VM only through `POST /api/v1/threads/{id}/irc`, with the same bearer authentication and owner scoping as `POST …/messages` (a revoked device fails like any other request). The agent sees an ordinary incoming agent message, labelled with the `from` the caller named, whichever token was used.
- **Outbound (the agent to you).** What a cloud agent writes to `agent://Parent` is delivered into your omp session as an incoming IRC message from that agent. As with a native subagent's message, it can wake an idle main agent. It is the agent's text, not yours. Content the agent read (an untrusted repository, a web page through its tools) can therefore reach your local model this way. omp frames it as an agent message; omp-cloud does not filter or sanitize it. When a message you sent woke an idle cloud agent, the turn's final reply returns to you as such a message too, in the `<task-result>` envelope described next. Treat it as you would a subagent's output.
- **Results are escaped.** A cloud agent's finished turn reaches the model as a `<task-result>` (and in `[cloud]` cards and op results as a `<cloud-output>` fence). In the reply, the error and the result lines, a `<` in front of omp's harness tags (`irc`, `system-…`) and of the envelope's own tags (`task-result`, `output`, `preview`, `meta`, `error`, `abort-reason`, `cloud-result`, `cloud-output`) becomes `&lt;`, so a hostile reply cannot close the envelope or forge a notice or an IRC message. This keeps the framing intact; the text is still the agent's, and still data, never instructions.
- **Limits.** Size and turn limits (32768 bytes, 200 turns) are in [IRC messages](api.md#irc-messages); an oversize message is cut with a marker, never silently.
- **Child jobs are display-only.** There is no remote cancel for them; to stop the work, stop the thread ([Cancelling](jobs.md#cancelling)).
- **Not verified.** These are descriptions of what the code does, checked by unit tests and the plugin scenario, not an audit; no test tries to break out through the extension or to inject hostile message text into a local session.

## GitHub App and signing key

Connecting GitHub ([GitHub](github.md)) puts two secrets on the service host and nothing in any VM:

- **The App's private key** (`<dataDir>/github/app.pem`) and **the signing key** (`<dataDir>/signing/ed25519.pem`) live under the data directory, each in a 0700 directory with mode 0600 files, written as a temporary file and renamed. The service refuses to use a key with group or other permission bits. They are in the [backups](operations.md), so the archive is as sensitive as the data directory. Disconnecting the App deletes its files, and deleting the signing key deletes its file; delete the App on GitHub as well to revoke it there.
- **Tokens never enter a VM.** The key signs a short JWT (10 minutes) that the service trades for an installation token scoped to one repository, valid for one hour. Git gets it for a single command and the service scrubs it from every error it records. A VM holds only the per-thread gateway client token, as before; a VM that is compromised cannot push, open a pull request or sign anything. Signing happens on the service, over the commits a VM made, so a VM controls the content of its own commits, as it always did, and not the key.
- **What the App may do.** It is created with Contents (write), Pull requests (write) and Metadata (read), no webhook and no events, private to the owner's account. It reaches only the repositories you install it on. It has **no Workflows permission**, so GitHub refuses a push that adds or changes `.github/workflows/*`: a cloud agent cannot rewrite your CI to reach repository secrets. The push policy applies unchanged: never forced, never a protected branch or the remote's default branch.
- **Only a connection with full access connects.** The GitHub and signing routes need full access ([API](api.md#tokens-and-callers)): a device with threads-only access cannot connect the App, make or delete the key, or read the key's registration. The manifest flow's `state` is random, kept in memory for an hour and used once, so a conversion that did not start on the service is refused.
- **Signed does not mean reviewed.** The service signs whatever a thread's agent committed, so Verified says the commit came through your service and its committer address is yours, not that the change is right. Pull requests open as drafts by default (`git.pr`) so you read them first.

## Secrets and MCP

The service's secrets and MCP support ([Secrets and MCP servers](secrets-and-mcp.md)) give a VM more than its gateway token, on purpose and only as far as you scope it:

- **Where the values live.** A literal secret and every MCP OAuth token are in the service database (`secrets`, `mcp_credentials`) as text, the way `update.token` is: what protects them is the data directory and the database file's permissions on the service host, not encryption. A `!command` secret stores the command, and its output is only cached in memory for 5 minutes; neither it nor a failure's output is logged or recorded in an event. An http MCP server's headers are in the thread's `secrets.json` (0600 in a 0700 directory), which is never served. All of it is in the [backups](operations.md): keep the archives as protected as the data directory, and never copy them off the host unencrypted.
- **What enters a VM.** Only (1) the secrets whose `repos` globs match the thread's repository key, (2) the thread's own `secretEnv` and `secretFiles`, and (3) its stdio MCP server entries (`command`, `args`, `cwd` and `env` references). Scoping is explicit: `repos` is required, an empty list is refused, and only `*` means every thread. No http MCP header and no MCP OAuth token enters a VM, and neither does a git or provider credential. The values sit in `~/.omp-cloud/env` (0600) and in omp's environment, so the agent, every tool it runs and anything it publishes can read them: a compromised or hostile repository's agent can exfiltrate what its VM holds, which is why a secret should be scoped to repositories you trust with it.
- **Read-only agents get no MCP servers.** With `policy.readOnly` on, no `mcp.json` and no MCP proxy token is delivered, so neither its stdio entries nor its http servers reach the VM. Its secrets and `secretEnv` still do; see [Read-only agents and plan mode](#read-only-agents-and-plan-mode).
- **Masking is not a boundary.** omp's obfuscation replaces known values in what it sends to the model. A value the agent transforms (encodes, splits, hashes) or writes into a file, a commit or a network request is not caught, and a value under 4 characters is not masked at all.
- **What reaches GitHub.** A turn's reply can hold a secret in clear (omp restores real values in what it prints). The pull request's title and omp-cloud section are scrubbed of every value the service delivered to the thread, as `[secret <NAME>]`, before they are posted, and nothing is posted when those values cannot be read ([GitHub](github.md#pull-requests)). The scrub knows the values it delivered and nothing else: a value the agent transformed, and the commits, branch and files it pushed, are not scrubbed.
- **Only a connection with full access manages them.** The secret routes, the MCP logins and the dashboard's Secrets page need full access ([API](api.md#tokens-and-callers)): a device with threads-only access cannot read the list, set or delete a secret, or log the service in to an MCP server. No route returns a value.
- **The MCP proxy.** It listens on the gateway address (`service.json` `mcp.listen`, `10.254.254.1:4100` from setup) and nowhere else, reachable by the VMs through the same exemption as the gateway and not by other machines through any of the three [listeners](api.md#listeners). A request must carry the bearer token made when its VM was provisioned: 32 random bytes of which only the SHA-256 is stored, replaced when a new VM is provisioned for the thread, refused for a failed thread, and good only for the http servers that thread shipped. Any process in the VM can use it, as it can use the gateway token. The service makes the upstream request, so the proxy is a place where a VM could try to reach things only the service host can: the create request refuses an http server URL that names a loopback, unspecified or link-local address, `localhost`, or the gateway or proxy address, and the proxy resolves the host again on every request and answers `403 the MCP server resolves to the service host` when any address is one of those. Redirects are never followed, so an upstream cannot send the proxy elsewhere. LAN addresses are allowed on purpose, for MCP servers on your own network: whoever may create a thread (a paired device included) names the URL, so the proxy reaches any LAN host that creator names, with the headers they supplied, but only with those. The proxy does not inspect what a server returns: its tool output reaches the agent and its model like any MCP server's.
- **OAuth logins are the service's, not a thread's.** A login made for a URL is used for every thread that ships that exact URL without its own `Authorization` header, as the model login serves every thread. Remove it by deleting the rows from `mcp_credentials` (there is no route yet) or revoke the grant at the MCP server.
- **What the settings filter does not do.** The plugin drops a fixed list of settings that hold credentials, paths or commands ([the list](secrets-and-mcp.md#settings-that-stay-on-your-machine)) and warns. It is not a scanner: a credential in another key, in an `AGENTS.md`, a skill or a rule, or in an `mcp.json` stdio `args` ships unchanged.

## Read-only agents and plan mode

`policy.readOnly` ([agent policy](api.md#agent-policy)) is on when the service's setting or the thread's request turns it on, never off from a thread.

- **What it enforces.** The push step never pushes, asks about or opens a pull request for a read-only thread, and the VM gets no MCP servers. A read-only thread's work stays on the service, readable through `diff`, `files` and `pull` (`pull` is the user's). It is a guard in the service's push step and provisioner, not a sandbox: the VM still runs with its secrets and its egress policy, and the line in its system prompt (`- Read-only:`, change nothing) is advice to the model.
- **Plan mode.** The plugin sets it on every delegation the model makes while omp is in plan mode, whatever the model passes, and refuses the model's `pull` and its messages to agents that are not read-only, because such a message would wake the agent and its next turn would push. The refusal reads the thread's own flag, so a service-wide `policy.readOnly` does not lift it for threads that did not set it. A plan-mode thread stays read-only for life; after the plan is approved the model delegates again. Your own `/cloud` commands are not restricted.
- **A replay cannot undo it.** An `Idempotency-Key` is bound to `policy.readOnly` as well as the prompt, so a delegation repeated with the same `ref` after plan mode ends is a conflict, not a replay of the read-only thread, and the reverse.

## Pairing by the model

The `cloud` tool's `connect` pairs this machine with a server the user named ([Pairing](pairing.md#over-ssh)). It asks you in a dialog (`Connect to omp-cloud?`, naming the target) and writes nothing when you decline or the dialog cannot be shown; it refuses when the machine is already paired and never replaces a pairing; and it never passes `--allow-public`, so a public address is refused as it is for `/cloud connect` ([Who may connect](pairing.md#who-may-connect)). Its tool approval is the exec tier. `use` only chooses among the clouds this machine already holds, once per session and only before the session has threads, and can pair nothing.

## Environments and previews

The VM toolchain, repository setup scripts and previews ([Environments and previews](environments.md)) each add something that runs or is served from inside a VM:

- **The recipe runs as root, in a throwaway VM, on the owner's say-so.** `vm.packages` and `vm.setup` run when the template is built, as root, with internet access, in a VM that holds no credential and is destroyed afterwards. Only the owner token and a device with full access change settings, so a device with threads-only access cannot change what runs as root in a template. Every thread's VM is made from the result: a line in `vm.setup` is in every VM.
- **A setup script is the repository's code, run by the service.** `.omp-cloud.yml` is committed by whoever wrote the repository, and a handoff ships it as it is, so the script runs even if you never read it. It runs as the VM's ordinary user in a sandbox of the template whose `app` is `omp-cloud-env`: it is not provisioned, so it holds no gateway client token and no omp config; the service's git and provider credentials are never there; the thread's egress policy (`policy.egress`) applies; and it ends, with its sandbox killed, after at most 30 minutes. It is isolated like a thread's VM, which means it can do whatever a thread's agent can do in its VM, and no more.
- **It sees the repository's Secrets.** The service's [Secrets](secrets-and-mcp.md#secrets) whose `repos` match the thread, scoped the way they are for a thread, are in the script's environment, so the script can read, use and send them wherever the VM's egress reaches. The thread's own `secretEnv` and `secretFiles` and MCP servers are not part of the build. The env file the values travel in is deleted before the script starts, but the values stay in the script's process environment. Scope a secret to repositories you trust with it ([Secrets and MCP servers](secrets-and-mcp.md#secrets)).
- **A snapshot keeps whatever the script wrote to disk.** An environment is the whole disk after the script. A secret the script wrote to a file (a `.npmrc` with a token, a credentialed cache, a `.env` it generated) is in the snapshot and in the disk of every VM started from it, readable by every thread on that repository whose key matches, until the environment is evicted or deleted. Snapshots are stored by vibemon on the service host, unencrypted, and are not in the [backups](operations.md). Do not write a secret to disk in a setup script, or delete it at its end.
- **The environment is built before any agent runs, and is only ever read after.** A thread's VM is created from a copy of the snapshot, and nothing a thread does writes back to it, so an agent cannot plant something for the next thread's VM through it. The key covers the template, the repository (`<host>/<path>`), the script and the contents of the cache files at the handoff commit, so a repository never gets another repository's environment. It does not cover the rest of the working tree: a script that reads files other than its `cacheFiles` is cached by those files alone ([Known limitations](architecture.md#known-limitations)).
- **Previews are bearer-only, and never on the dashboard's origin.** `/api/v1/threads/{id}/ports/{port}` needs the owner token or a device token, and the dashboard listener, whose session cookie is the owner's, answers `404` for it, so a page that a VM serves can never run with that cookie. Anyone who holds such a token could already message the thread's agent, and gets no more than a web request to one of the VM's ports; the caller's `Authorization` header and `x-omp-*` and `e2b-*` headers are not forwarded, and the VM's own control port (49983) is refused.
- **The browser is the weak end of a preview.** A page the VM serves is untrusted content (the agent, or a hostile repository, wrote it) running in your browser at `http://localhost:<lp>/`. The plugin's forwarder answers only that host name, so the page does not share `127.0.0.1`, where the dashboard's `omp_cloud_session` cookie lives, and it removes that cookie from what it relays in both directions. It cannot keep other servers on your machine out of reach: cookies are scoped by host, not port, so cookies of other local servers set for `localhost` are sent to the forwarder and relayed to the VM's server, and the page can make requests to other `localhost` ports like any web page can. Preview only what you would open from the cloud, and stop it with `/cloud preview stop`.
- **A model-driven preview puts the page in front of the model.** The `cloud` tool's `preview` op lets the local model start a forwarder and open it with its browser tool. What the page says (it is the agent's, or a hostile repository's, own content) is then input to the model, like any web page it browses, and a page it opens runs in the browser that tool drives. The op asks for the same approval as `send`; it adds no new route and no new token: the forwarder is the one `/cloud preview` starts, with the same host restriction.

## Memory

Cloud agents run without memory ([Memory](commands.md#memory)), so memory crosses the boundary in neither direction:

- **Out: your memory never goes to a VM.** A handoff ships no `~/.omp/agent/memories`, so no project's memories (and no other project's) can be read by an agent, or by anything it reads or runs, in a VM. omp in the VM runs with `memory.backend: off` (set by the service's config, which wins over your shipped `config.yml` and overlays), so it neither recalls nor stores.
- **In: cloud agents cannot write into your local recall.** Nothing the VM remembered is exported, downloaded or merged, so a cloud agent working on an untrusted repository, or one that read a hostile page, cannot plant memories your local agent would later recall as if you had retained them. What your omp learns from a cloud result is what it retains itself from the reply, the diff or the saved session, which still is a cloud agent's output: [treat it as a subagent's](#messages-between-your-omp-and-a-cloud-agent).
