# Security model

[README](../README.md) · [Documentation index](../README.md#documentation)

What the service, the VMs and your devices can reach, what runs as root, and what crosses between your omp and a cloud agent.

## Trust boundaries

- The service has three listeners, defined in [API](api.md#listeners): the API listener (`listen`, plain HTTP, loopback only) for the owner token and this machine's devices, the dashboard listener (`dashboard.listen`, plain HTTP, loopback only) for the dashboard's session cookie, and the remote listener (`remote`, TLS, set up on `0.0.0.0:8443`) for paired devices only. The owner token is refused on the remote listener; the dashboard listener's `POST /session` accepts it to open a session.
- The remote listener is the only omp-cloud listener reachable from other machines. vibemon and the auth broker listen on loopback, and the gateway and the [MCP proxy](#secrets-and-mcp) on `10.254.254.1`. The service is the only vibemon client.
- A VM holds one per-thread gateway client token. Provider credentials and git credentials never enter it. What else reaches it is what you scope to it: the service's [secrets](#secrets-and-mcp) whose `repos` match the thread's repository, the thread's own `secretEnv` and `secretFiles`, and the entries of its stdio MCP servers.
- The cloud broker has its own OAuth login (`/cloud login <provider>`); yours is never copied.
- VM egress: the internet, plus the gateway IP. vibemon runs with `--egress-internal-allow 10.254.254.1/32`, so every other private range is denied. That exemption covers every port of the address, and a VM's traffic reaches the service host from it, so a host listener bound to all addresses is reachable from VMs; the remote listener refuses that source. `policy.egress` narrows the internet to a list for new VMs.
- `bash.patterns` (and the fixed git guard in the VM) is a guard, not a boundary: its globs see the command text with quotes removed and over-match, and `g=git; $g pus"h"` evades them. The boundaries are the missing credentials, the push policy and egress.

## What runs as root

- **Setup.** `omp-cloud setup` runs as your user and calls `sudo` once, for one command (`omp-cloud setup system …`): packages, the vibemon install, two system units and the helper below. It refuses to run as root, and the sudo password prompt is yours: setup never supplies or caches it. `omp-cloud uninstall` does the same in reverse. Setup never changes firewall rules.
- **The helper and its sudoers rule.** `/usr/local/libexec/omp-cloud/vmon-install` is root-owned (0755) and is the only thing `/etc/sudoers.d/omp-cloud` (0440, checked with `visudo -cf`) lets your user run without a password. The rule never covers the `omp-cloud` binary, which your user owns and can replace. The helper takes one argument, a vibemon tag, and downloads, verifies and installs only that release ([Updating](updating.md#vibemon-is-pinned)); the updater uses it so a one-click update that moves vibemon needs no password.
- **System units.** `omp-cloud-net` (the dummy `ompsvc0` link at `10.254.254.1`, the only address sandboxes reach on the host) and `vmon` (vibemon) are system services; the omp-cloud service, the auth broker, the gateway and the backup timer are your user's units and never run as root.
- **Linger.** Setup runs `loginctl enable-linger` for your user so those user units start at boot without a login, records that in `/etc/omp-cloud/setup.json`, and `uninstall` undoes only what setup enabled (`--no-linger` skips it).

## Messages between your omp and a cloud agent

A cloud agent can be messaged from your omp and can message it back, the way omp's own agents message each other ([Messaging a cloud agent](jobs.md#messaging-a-cloud-agent); the endpoint is [IRC messages](api.md#irc-messages)). This adds a channel across the trust boundary above. What matters for trust:

- **The VM extension.** `irc-peer.ts` runs in each VM's omp with the VM agent's own privileges, inside the VM's limits (the gateway-only egress above, no git or provider credentials). Its only host import is omp's `registry/agent-registry`; apart from `node:` built-ins it imports nothing and opens no sockets. An outgoing message leaves as a status frame on omp's stdout, which the runner already reads.
- **Inbound (you to the agent).** A message reaches a VM only through `POST /api/v1/threads/{id}/irc`, with the same bearer authentication and owner scoping as `POST …/messages` (a revoked device fails like any other request). The agent sees an ordinary incoming agent message, labelled with the `from` the caller named, whichever token was used.
- **Outbound (the agent to you).** What a cloud agent writes to `agent://Parent` is delivered into your omp session as an incoming IRC message from that agent. As with a native subagent's message, it can wake an idle main agent. It is the agent's text, not yours. Content the agent read (an untrusted repository, a web page through its tools) can therefore reach your local model this way. omp frames it as an agent message; omp-cloud does not filter or sanitize it. When a message you sent woke an idle cloud agent, the turn's final reply returns to you as such a message too. Treat it as you would a subagent's output.
- **Limits.** Size and turn limits (32768 bytes, 200 turns) are in [IRC messages](api.md#irc-messages); an oversize message is cut with a marker, never silently.
- **Child jobs are display-only.** There is no remote cancel for them; to stop the work, stop the thread ([Cancelling](jobs.md#cancelling)).
- **Not verified.** These are descriptions of what the code does, checked by unit tests and the plugin scenario, not an audit; no test tries to break out through the extension or to inject hostile message text into a local session.

## GitHub App and signing key

Connecting GitHub ([GitHub](github.md)) puts two secrets on the service host and nothing in any VM:

- **The App's private key** (`<dataDir>/github/app.pem`) and **the signing key** (`<dataDir>/signing/ed25519.pem`) live under the data directory, each in a 0700 directory with mode 0600 files, written as a temporary file and renamed. The service refuses to use a key with group or other permission bits. They are in the [backups](operations.md), so the archive is as sensitive as the data directory. Disconnecting the App deletes its files, and deleting the signing key deletes its file; delete the App on GitHub as well to revoke it there.
- **Tokens never enter a VM.** The key signs a short JWT (10 minutes) that the service trades for an installation token scoped to one repository, valid for one hour. Git gets it for a single command and the service scrubs it from every error it records. A VM holds only the per-thread gateway client token, as before; a VM that is compromised cannot push, open a pull request or sign anything. Signing happens on the service, over the commits a VM made, so a VM controls the content of its own commits, as it always did, and not the key.
- **What the App may do.** It is created with Contents (write), Pull requests (write) and Metadata (read), no webhook and no events, private to the owner's account. It reaches only the repositories you install it on. It has **no Workflows permission**, so GitHub refuses a push that adds or changes `.github/workflows/*`: a cloud agent cannot rewrite your CI to reach repository secrets. The push policy applies unchanged: never forced, never a protected branch or the remote's default branch.
- **Only the owner connects.** The GitHub and signing routes are owner-token only ([API](api.md#tokens-and-callers)): a paired device cannot connect the App, make or delete the key, or read the key's registration. The manifest flow's `state` is random, kept in memory for an hour and used once, so a conversion that did not start on the service is refused.
- **Signed does not mean reviewed.** The service signs whatever a thread's agent committed, so Verified says the commit came through your service and its committer address is yours, not that the change is right. Pull requests open as drafts by default (`git.pr`) so you read them first.

## Secrets and MCP

The service's secrets and MCP support ([Secrets and MCP servers](secrets-and-mcp.md)) give a VM more than its gateway token, on purpose and only as far as you scope it:

- **Where the values live.** A literal secret and every MCP OAuth token are in the service database (`secrets`, `mcp_credentials`) as text, the way `update.token` is: what protects them is the data directory and the database file's permissions on the service host, not encryption. A `!command` secret stores the command, and its output is only cached in memory for 5 minutes; neither it nor a failure's output is logged or recorded in an event. An http MCP server's headers are in the thread's `secrets.json` (0600 in a 0700 directory), which is never served. All of it is in the [backups](operations.md): keep the archives as protected as the data directory, and never copy them off the host unencrypted.
- **What enters a VM.** Only (1) the secrets whose `repos` globs match the thread's repository key, (2) the thread's own `secretEnv` and `secretFiles`, and (3) its stdio MCP server entries (`command`, `args`, `cwd` and `env` references). Scoping is explicit: `repos` is required, an empty list is refused, and only `*` means every thread. No http MCP header and no MCP OAuth token enters a VM, and neither does a git or provider credential. The values sit in `~/.omp-cloud/env` (0600) and in omp's environment, so the agent, every tool it runs and anything it publishes can read them: a compromised or hostile repository's agent can exfiltrate what its VM holds, which is why a secret should be scoped to repositories you trust with it.
- **Masking is not a boundary.** omp's obfuscation replaces known values in what it sends to the model. A value the agent transforms (encodes, splits, hashes) or writes into a file, a commit or a network request is not caught, and a value under 4 characters is not masked at all.
- **Only the owner manages them.** The secret routes, the MCP logins and the dashboard's Secrets page are owner-token only ([API](api.md#tokens-and-callers)): a paired device cannot read the list, set or delete a secret, or log the service in to an MCP server. No route returns a value.
- **The MCP proxy.** It listens on the gateway address (`service.json` `mcp.listen`, `10.254.254.1:4100` from setup) and nowhere else, reachable by the VMs through the same exemption as the gateway and not by other machines through any of the three [listeners](api.md#listeners). A request must carry the bearer token made when its VM was provisioned: 32 random bytes of which only the SHA-256 is stored, replaced when a new VM is provisioned for the thread, refused for a failed thread, and good only for the http servers that thread shipped. Any process in the VM can use it, as it can use the gateway token. The service makes the upstream request, so the proxy is a place where a VM could try to reach things only the service host can: the create request refuses an http server URL that names a loopback, unspecified or link-local address, `localhost`, or the gateway or proxy address, and the proxy resolves the host again on every request and answers `403 the MCP server resolves to the service host` when any address is one of those. Redirects are never followed, so an upstream cannot send the proxy elsewhere. LAN addresses are allowed on purpose, for MCP servers on your own network: whoever may create a thread (a paired device included) names the URL, so the proxy reaches any LAN host that creator names, with the headers they supplied, but only with those. The proxy does not inspect what a server returns: its tool output reaches the agent and its model like any MCP server's.
- **OAuth logins are the service's, not a thread's.** A login made for a URL is used for every thread that ships that exact URL without its own `Authorization` header, as the model login serves every thread. Remove it by deleting the rows from `mcp_credentials` (there is no route yet) or revoke the grant at the MCP server.
- **What the settings filter does not do.** The plugin drops a fixed list of settings that hold credentials, paths or commands ([the list](secrets-and-mcp.md#settings-that-stay-on-your-machine)) and warns. It is not a scanner: a credential in another key, in an `AGENTS.md`, a skill or a rule, or in an `mcp.json` stdio `args` ships unchanged.

## Cloud memories

Memory parity ([Memory](commands.md#memory)) moves memory in both directions, and each direction has its own trust question:

- **Out: your memory goes to a VM.** A handoff ships `~/.omp/agent/memories/mnemopi`, as it always did, so the cloud agent can recall what you retained. The agent, and anything it reads or runs in the VM, can read all of it, every bank and not only the project's. If something is in your Mnemopi store that a repository's agent must not see, keep it out of the store or do not hand that repository off.
- **In: cloud memories enter your local recall.** What the cloud agent retains is merged into your local Mnemopi store, the one your omp recalls from in later sessions. A cloud agent working on an untrusted repository, or one that read a hostile page, can therefore write memories (text, not code) that your local agent later recalls as if you had retained them. Rows from the cloud are ordinary memory rows and nothing marks them as coming from the cloud. Treat what a cloud agent remembered as you treat its replies, and delete a row you do not trust from your store.
- **The VM's database is untrusted input.** The service exports it with `VACUUM INTO` and stores and serves the tar without reading it. Your plugin checks the archive before it extracts anything: only the members `./`, `./mnemopi.db`, `./banks/`, `./banks/<name>/` and `./banks/<name>/mnemopi.db` (a `<name>` of 1 to 64 letters, digits, `_` and `-`) are accepted, and any other member rejects the whole archive with `unexpected entry <name>`; a database that is not a plain file, or has more than one hard link, is refused. The VM's database is then attached to yours with `trusted_schema` off, so a view, trigger or default in its schema cannot call SQL functions, and only the columns both databases have, of `working_memory` and `annotations`, are copied, in one transaction per database that a failure rolls back. A failed merge is reported as `☁ could not merge the cloud memories of <id>: <reason>`, never as a failed pull.
- **Limits of that.** The check keeps the VM from choosing files on your machine and from running SQL through its schema, and the merge copies only values. It cannot judge the text of a memory. When your machine has no database yet for the default store or the project bank, the VM's file is copied into place as it is, so its schema and its rows (every one, not only those created after the thread began) become yours; this happens only the first time, before your own memory exists. The export is capped at 64 MiB.
- **Who can read it.** `GET /api/v1/threads/{id}/memory` serves the export to the owner and to a paired device, like the conversation and the result. It is in the [backups](operations.md) with the thread's other files.
