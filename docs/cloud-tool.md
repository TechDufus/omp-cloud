# The `cloud` tool

[README](../README.md) · [Documentation index](../README.md#documentation)

The local model can delegate to the cloud and manage the threads it started, through one tool with an `op` field (named `cloud`, or `cloud_agent` when another tool already has that name). The tool's own description tells the model when to use it: work that is independent of this machine and long-running or parallel (broad refactors, test suites, research or review reports, batch jobs, several independent tasks at once), not quick edits or anything that needs this machine's services or secrets. Ops:

- `delegate` starts one thread with `task`, or 1 to 8 with `tasks` (one snapshot is shared and at most 4 uploads run at once; `context` is prepended to every task's prompt, and `model`, `thinking`, `policy`, `workspace`, `conversation` and `wip` given beside `tasks` are the defaults of each). A task can set `name`, `ref`, `model`, `thinking`, `policy` (it can only tighten the service's limits: `spend.turnUSD`, `spend.threadUSD`, `egress`, `fetch`, `webSearch`, `browser`), `workspace`, `conversation: "none"` (ship no conversation) and `wip: false` (ship no uncommitted work). Inside a git repository with a commit the cloud agent gets the repository including uncommitted work; outside one, or with `workspace: "scratch"`, it works in an empty repository (a [scratch thread](#scratch-threads)). A `ref` (1 to 64 of `A-Z a-z 0-9 . _ -`) names the thread and makes the call safe to repeat: the same `ref` with the same task replays the first thread instead of creating a second (the result says `replayed`), and the same `ref` with a different task is refused (`conflict`: use another ref or none). Two tasks of one call cannot share a `ref`.
- `list` pages through threads, newest first (`filter`: `phase`, `origin`, `mine`, `repo`, `ref`, `since`; `limit` 20 by default, 100 at most; `N of total` and a cursor). `status` shows one or several threads (phase, current activity, cost and context, who follows it, a pending question with its kind and expiry, recent turns and the result). `read` pages the full text of a turn's reply, error or prompt (without a page asked, the latest result is `agent://<id>`, which omp's own `read` shows too). `events` lists what the agent did. `diff` and `files` read the change and the files of its result without pulling it. `info` shows the service version and capabilities, models, limits and today's spend against the day cap.
- `send` queues a message. In the default queue mode it is the same path as `write agent://<id>` ([jobs](jobs.md#messaging-a-cloud-agent)): an idle thread is woken (`delivered: woken; turn N queued`), a running turn gets the message at its next step (`delivered: into the running turn at its next step (injected)`), an archived thread is revived, and `details.receipt` carries omp's receipt; a service without the `threads.irc` capability queues it as a turn. `mode: "interrupt"` stops the running turn, cancels the turns queued behind it and runs the message next (the result lists the cancelled turns). A thread that failed takes no more messages (`conflict`). A slash command is sent to the cloud agent's own omp. `stop` takes one thread, a list, or `"all-mine"`. `delete` needs `confirm: true`, and a thread the model did not start in this session also `force: true`.
- `answer` answers a question of the kind `ask`. Tool approvals and push questions are the user's decision: the tool refuses them (`forbidden`) and tells the model to say so, and you answer with `/cloud answer` or the card buttons.
- `wait` blocks until threads settle (done, failed or a question), on named threads or, without any, on every thread the model started in this session that is working or waiting; `until` is `any` (the default) or `all`, and `on` narrows what ends the wait. It returns per-thread outcomes (`done`, `failed`, `question`, `deleted`, `timeout`, `stale`) and the call to make next. The default timeout is 10 minutes (`timeoutSec`, at most 30 minutes); a timeout is a result, not an error.
- `pull` brings a result into the local repository: `fetch` (the default; branch `omp-cloud/<id>`, working tree untouched), `merge` (fast-forward the current branch; refused on a dirty tree or a detached HEAD) or `worktree` (a new checkout; `into` names it, else `<repo>-<short id>` beside the repository; refused when a worktree already holds the branch or the directory is not empty). It refuses a repository the thread did not start from unless `force` is set (your own `/cloud pull`, the hub and the card's Pull button skip that check, because you name the thread). A branch that is checked out in another worktree is fast-forwarded there, and a worktree that cannot fast-forward refuses with a `conflict` naming it. A scratch thread is cloned into the new directory `into`.

Threads the model starts come back to it without polling: a finished turn as omp's async-result of the thread's job, a question as a `[cloud]` card, and `wait` returns the result itself when it is blocked on the job. A thread that is no longer working settles a `wait` with its real outcome, whatever `on` says. Adoption of a thread you started, a lost connection and a deleted thread are in [how results arrive](jobs.md#how-results-arrive).

Every result starts `cloud <op>: ok …` or, for a failure, `cloud <op>: error <code>: <message>`, with a hint and a line saying whether retrying can help. The codes are `invalid`, `not_found`, `ambiguous_ref` (a reference matched several threads; the candidates are listed), `conflict`, `forbidden`, `unauthorized` (a revoked device must `/cloud connect` again), `not_configured`, `unreachable`, `timeout`, `ambiguous_outcome`, `too_large`, `rate_limited`, `unavailable`, `capacity`, `aborted` and `version_skew` (the service lacks a feature of this plugin: update it, see [Updating](updating.md)).

Retries: the model's reads, `stop`, `answer`, `delete` and a create that carries a `ref` retry themselves up to three times (about 0.5 s, 1.5 s and 4 s, honouring `Retry-After` up to 30 s); your own `/cloud` commands, the hub, the card buttons, `/cloud <task>`, `/cloud status` and `/cloud disconnect` retry once after at most 0.25 s (`Retry-After` up to 1 s). A retried write that finally fails after an attempt that may have been delivered reports that its outcome is unknown, and a `delegate` then says `repeat with ref: <key>`, so repeating the same call replays the first thread instead of creating another. A retried `delete` that finds the thread already gone counts as done, and a retried `answer` whose question already holds the same answer counts as answered. A queue-mode `send` carries a message id, so it retries safely (up to four attempts, all with that id; the service answers a repeated id as the first time): when every attempt fails without an answer, the error says the message may have been delivered. A `send` with `mode: "interrupt"` is never repeated: when its answer is lost the result is `ambiguous_outcome` ("the request may have been received"), and the model checks the thread before sending again.

Every op that takes `thread` accepts the references `/cloud` commands take ([thread references](commands.md#cloud-commands)); `status`, `stop`, `wait` and `delete` also take a list.

## Native views

In Tern the tool's calls and results draw natively instead of as text: `wait` and `status` as job tiles under omp's own wait head (`waiting on N of M jobs`, `M jobs settled`, counts of done, failed and cancelled), `list` as tiles in a section per repository, and the other ops as key-value, text, code and diff blocks. A call's partial view is replaced by its result view. A terminal UI and the model see the text result.

## Scratch threads

`/cloud` hands off the repository you are in. For work that needs none, such as research, a review of a pasted document or a scratch script, the model delegates with `workspace: "scratch"` (the default outside a git repository, or in one without a commit): the cloud agent starts in an empty repository, nothing of your machine's files is shipped, and its result is an ordinary branch. `/cloud pull <id> --into <dir>` (or `pull` with `into`) clones it into a new directory.
