# The `cloud` tool

[README](../README.md) · [Documentation index](../README.md#documentation)

The local model can delegate to the cloud and manage the threads it started, through one tool with an `op` field (named `cloud`, or `cloud_agent` when another tool already has that name). A cloud agent works like a `task` subagent: an agent the model starts begins blank (it gets `context` and `task`, not the conversation, and has no omp memory), has no `ask` tool, and its final message is its result, delivered as a `<task-result>` ([how results arrive](jobs.md#how-results-arrive)). The tool's description tells the model when to delegate: work that is independent of this machine and long-running or parallel (broad refactors, test suites, research or review reports, work that needs a VM of its own, batch jobs, several independent tasks at once), not quick edits or anything that needs this machine's services, files or display. It also tells the model what a cloud agent has (the repository with uncommitted work unless `wip: false`, your omp setup, the MCP servers of your `mcp.json` that can ship, the service's [Secrets](secrets-and-mcp.md#secrets) for the repository as environment variables, a Debian VM with sudo and the toolchain `info` lists, and the web as the policy allows) and what happens to its work (committed to `omp-cloud/<thread>`, pushed as the owner's `git.push` says, then a draft pull request: [GitHub](github.md#pull-requests)). A cloud agent cannot reach this machine, and the model is told never to put a credential in a task. One cloud serves a session ([picking a cloud](#picking-a-cloud)). Ops:

- `delegate` starts one thread with `task`, or 1 to 8 with `tasks` (one snapshot is shared and at most 4 uploads run at once; `context` is prepended to every task's prompt, and `model`, `thinking`, `policy`, `workspace`, `conversation` and `wip` given beside `tasks` are the defaults of each). A task can set `name` (a short human title, at most 60 characters, which titles the pull request; the agent's id is its CamelCase form), `ref`, `model`, `thinking`, `policy` (it can only tighten the service's limits: `spend.turnUSD`, `spend.threadUSD`, `egress`, `fetch`, `webSearch`, `browser`, `readOnly`), `workspace`, `conversation` and `wip: false` (ship no uncommitted work). A delegation ships no conversation unless `conversation: "full"` forks this one into the agent; your own `/cloud <task>` always forks it. Inside a git repository with a commit the cloud agent gets the repository including uncommitted work; outside one, or with `workspace: "scratch"`, it works in an empty repository (a [scratch thread](#scratch-threads)). A `ref` (1 to 64 of `A-Z a-z 0-9 . _ -`) names the thread and makes the call safe to repeat: the same `ref` with the same task replays the first thread instead of creating a second (the result says `replayed`), and the same `ref` with a different task or read-only setting is refused (`conflict`: use another ref or none). Two tasks of one call cannot share a `ref`. [What it returns](#what-delegate-returns), [models](#models-and-logins) and [plan mode](#plan-mode) are below.
- `list` pages through threads, newest first (`filter`: `phase`, `origin`, `mine`, `repo`, `ref`, `since`; `limit` 20 by default, 100 at most; `N of total` and a cursor). `status` shows one or several threads (phase, current activity, cost and context, who follows it, a pending question with its kind and expiry, recent turns, the result and, once the service opened one, the pull request as `pr: <url>`). `read` pages the full text of a turn's reply, error or prompt (without a page asked, the latest result is `agent://<id>`, which omp's own `read` shows too). `events` lists what the agent did. `diff` and `files` read the change and the files of its result without pulling it. `info` shows the clouds this machine knows and the one this session uses, the service as `service: <name> · omp-cloud <version> (api N) · you: <who>` (the cloud's name, and the owner with the owner token, the owner on a device with full access, or a device with threads-only access), its capabilities, models (the default model and whether this session's model is served), what cloud agents may do and what happens to their work ([below](#what-info-says-about-agents)), limits, today's spend against the day cap, the VMs, `capacity:` (the vibemon cluster's vCPU, memory, machines and VMs against the limit, or why it is unavailable) and `update: <mode> · <state>`. The `caller` detail carries the caller's `access`.
- `send` queues a message. In the default queue mode it is the same path as `write agent://<id>` ([jobs](jobs.md#messaging-a-cloud-agent)): an idle thread is woken (`delivered: woken; turn N queued`), a running turn gets the message at its next step (`delivered: into the running turn at its next step (injected)`), an archived thread is revived, and `details.receipt` carries omp's receipt; a service without the `threads.irc` capability queues it as a turn. With the default `follow: "wake"` the reply comes back to the model like a subagent's, and `follow: "silent"` leaves delivery as it is. `mode: "interrupt"` stops the running turn, cancels the turns queued behind it and runs the message next (the result lists the cancelled turns). A thread that failed takes no more messages (`conflict`). In [plan mode](#plan-mode) a message to an agent that is not read-only is refused. A slash command is sent to the cloud agent's own omp. `stop` takes one thread, a list, or `"all-mine"`. `delete` needs `confirm: true`, and a thread the model did not start in this session also `force: true`.
- `answer` answers a question of the kind `ask`. Agents the model starts have no `ask` (an agent that needs a decision ends its turn with the question as its result, and the model answers by messaging it), so only a thread you started that the model adopted, or one on a service without the capability `threads.subagent`, asks. Tool approvals and push questions are the user's decision: the tool refuses them (`forbidden`) and tells the model to say so, and you answer with `/cloud answer` or the card buttons.
- `wait` blocks until threads settle (done, failed or a question), on named threads or, without any, on every thread the model started in this session that is working or waiting; `until` is `any` (the default) or `all`, and `on` narrows what ends the wait. omp's own `wait` already covers the agents the model started; this one serves named threads and threads you started. It returns per-thread outcomes (`done`, `failed`, `question`, `deleted`, `timeout`, `stale`), the `<task-result>` of a job it was blocked on, and the call to make next. The default timeout is 10 minutes (`timeoutSec`, at most 30 minutes); a timeout is a result, not an error.
- `pull` brings a result into the local repository: `fetch` (the default; branch `omp-cloud/<id>`, working tree untouched), `merge` (fast-forward the current branch; refused on a dirty tree or a detached HEAD) or `worktree` (a new checkout; `into` names it, else `<repo>-<short id>` beside the repository; refused when a worktree already holds the branch or the directory is not empty). It refuses a repository the thread did not start from unless `force` is set (your own `/cloud pull`, the hub and the card's Pull button skip that check, because you name the thread). A branch that is checked out in another worktree is fast-forwarded there, and a worktree that cannot fast-forward refuses with a `conflict` naming it. A scratch thread is cloned into the new directory `into`. In plan mode `pull` is refused (`forbidden`): it changes this repository, and `diff` and `files` read the result instead.
- `preview` lets the model look at a web app or dev server a cloud agent runs in its VM. `{op: "preview", thread, port}` starts the same forwarder `/cloud preview <id> <port>` does ([Previews](commands.md#previews)) and returns its address, `cloud preview: ok http://localhost:<lp>/ → port <port> of <thread id> (<name>)`, with a line that tells the model to open it with its browser tool (to screenshot, click or read the page), that a paused VM wakes on the first request, that WebSockets are not forwarded, and how to stop it. `port` is 1 to 65535 and not 49983 (`invalid`); a service without the capability `threads.preview` answers `version_skew`. A second call for the same thread and port returns the same address, and so does one for a preview you started with `/cloud preview`. `{op: "preview", stop: true}` ends every preview and answers `cloud preview: ok stopped <n> previews`; with `thread` (and `port`) it ends only those. The previews are one list: `/cloud preview stop`, `/cloud disconnect` and ending omp end the ones the model started too. The call needs approval like `send` (it opens a listener on this machine), and the page it opens is the agent's own content ([Security model](security.md#environments-and-previews)). The prompt of an agent the model started tells it to start its server detached (`setsid nohup <command> >/dev/null 2>&1 &`, listening on `127.0.0.1` is enough, never on port 49983) and to name the port in its result. Preview works in plan mode.
- `use` picks the cloud this session uses, by where it is configured: `{op: "use", cloud: "env" | "personal" | "paired"}` (the same choice as `/cloud use`). It is refused with `conflict` once the session has cloud threads, and with `invalid` when this machine has no usable cloud of that kind. [Picking a cloud](#picking-a-cloud).
- `connect` pairs a cloud the user named: `{op: "connect", target}` with `user@host`, `host`, `ssh://[user@]host[:port]` or a pairing code `ompc1:…`. You confirm the `Connect to omp-cloud?` dialog first; the tool never replaces a pairing and never passes `--allow-public`. Its approval is the exec tier (`pairs this machine with an omp-cloud server as one of its devices`). The session then uses the new cloud when it has no threads.

Threads the model starts come back to it without polling: a finished turn as omp's async-result of the thread's job, rendered as a `<task-result>` like a `task` subagent's, a question of an adopted thread as a `[cloud]` card, and `wait` returns the result itself when it is blocked on the job. A turn a message woke (`send`, `write agent://<id>`) is delivered once, as the wake relay's incoming message from the agent: no `[cloud]` card, and a `wait` on its job returns a pointer to that message. The delegation itself posts no card either: the `delegate` result is its record. A thread that is no longer working settles a `wait` with its real outcome, whatever `on` says. Adoption of a thread you started, a lost connection and a deleted thread are in [how results arrive](jobs.md#how-results-arrive).

Every result starts `cloud <op>: ok …` or, for a failure, `cloud <op>: error <code>: <message>`, with a hint and a line saying whether retrying can help. The codes are `invalid`, `not_found`, `ambiguous_ref` (a reference matched several threads; the candidates are listed), `conflict`, `forbidden`, `unauthorized` (a revoked device must `/cloud connect` again), `not_configured` (no cloud is configured, or the cloud has no model login; the hint tells the model to ask you, and to use `connect` only when you ask it to), `unreachable`, `timeout`, `ambiguous_outcome`, `too_large`, `rate_limited`, `unavailable`, `capacity`, `aborted` and `version_skew` (the service lacks a feature of this plugin: update it, see [Updating](updating.md)). What a cloud agent says is data: it comes in the `<task-result>` or a `<cloud-output>` fence, with omp's harness tags in it escaped ([Security model](security.md#messages-between-your-omp-and-a-cloud-agent)).

Retries: the model's reads, `stop`, `answer`, `delete` and a create that carries a `ref` retry themselves up to three times (about 0.5 s, 1.5 s and 4 s, honouring `Retry-After` up to 30 s); your own `/cloud` commands, the hub, the card buttons, `/cloud <task>`, `/cloud status` and `/cloud disconnect` retry once after at most 0.25 s (`Retry-After` up to 1 s). A retried write that finally fails after an attempt that may have been delivered reports that its outcome is unknown, and a `delegate` then says `repeat with ref: <key>`, so repeating the same call replays the first thread instead of creating another. A retried `delete` that finds the thread already gone counts as done, and a retried `answer` whose question already holds the same answer counts as answered. A queue-mode `send` carries a message id, so it retries safely (up to four attempts, all with that id; the service answers a repeated id as the first time): when every attempt fails without an answer, the error says the message may have been delivered. A `send` with `mode: "interrupt"` is never repeated: when its answer is lost the result is `ambiguous_outcome` ("the request may have been received"), and the model checks the thread before sending again.

Every op that takes `thread` accepts the references `/cloud` commands take ([thread references](commands.md#cloud-commands)); `status`, `stop`, `wait` and `delete` also take a list.

## What delegate returns

Each started task answers with ``task N: agent `<Name>` (thread <id>) started`` (``found again (replayed)`` for a repeated `ref`). `<Name>` is the agent's id: the CamelCase form of its name, the omp job id, and what `agent://<Name>` reads. Below it: `workspace`, `model`, `ref`, `read-only: nothing it changes is pushed, and it has no MCP servers` for a read-only agent, `conversation: forked from this session` (or `too large, not shipped`; nothing for none) and any `warnings`. Once per call comes `mcp servers: <name> (through the service | in the VM), …` for the MCP servers of your `mcp.json` that shipped, and the last line is `next: results auto-deliver as <task-result>; NEVER poll. Completely blocked? Call wait. agent://<id> reads a result; write agent://<id> messages an agent`. Against a service without `threads.subagent` a `warnings:` line adds `this service predates subagent threads: its agents may ask questions, which arrive as [cloud] messages (answer with cloud answer)`.

## Models and logins

The cloud agent runs the session's model unless `model` names another. When the session's model is not one the cloud serves and the model named none, the cloud's default model runs (the thinking level stays as resolved) and `warnings` says so: `this session's model <m> is not served by this cloud; it runs the cloud's default model <d>`. A model the call named that the cloud does not serve (or a session model with no served default to fall back on) is `invalid` (`this cloud does not serve <model>`), and its hint lists up to five served ids and tells the model to ask you to log the cloud in. A cloud with no model login at all is `not_configured` (`this cloud has no model login yet`) with the hint `ask the user to run /cloud login <provider>`, which is `omp-cloud login <provider>` on the server machine (over ssh: `ssh -t <user>@<host> '~/.local/bin/omp-cloud login <provider>'`) when this machine is a paired device. The tool never starts a login; your own `/cloud <task>` can ([commands](commands.md#cloud-commands)).

## Plan mode

While omp is in plan mode, a delegation is a read-only agent, as omp's own subagents are: `policy.readOnly` is set on every task, whatever the model passed. Nothing such an agent changes is pushed or opened as a pull request, it gets no MCP servers, and it is told to change nothing; it stays read-only for life, so the model delegates again after the plan is approved for work that should land. A service without the capability `threads.readonly` fails the call with `version_skew` before anything is uploaded (`plan mode delegates read-only cloud agents, and this service cannot run them`). A `ref` reused after the switch is a `conflict` (`different task or read-only setting`), never a replay.

Plan mode also refuses what would change this repository or wake a writable agent: `pull` (`forbidden`, `plan mode: pull changes this repository`), and `send` or `write agent://<id>` to an agent that is not read-only (`forbidden`, `plan mode: <id> is not read-only, so a message could make it change and push work`). `list`, `status`, the reads, `diff`, `files`, `preview`, `use`, `connect`, `stop` and `delete` work, `answer` stays open (the turn that asked runs on whether or not it is answered), and so does the hub's chat box. Your own `/cloud` commands act as typed. The guard reads the thread's own flag, so a service-wide `policy.readOnly` does not make it let messages through. `info` says `plan mode: on` while it applies. Why it is built this way: [architecture](architecture.md#design).

## Picking a cloud

A session uses one cloud, by default the first of `OMP_CLOUD_URL` (`env`), the `url` and `token` of your `config.yml` (`personal`) and the pairing of `connection.json` (`paired`) ([configuration](configuration.md#client-config)). `info` starts with `cloud: <source> · <url> · <why>` (`the default (…)` or `this session's choice`) and `other clouds: <source> <url> (<where>), …`, and a failing `info` with `not_configured` lists them too. `use` switches the session, as long as it has launched or adopted no thread; the choice is stored in the session as an `omp-cloud-target` entry, so a resumed session keeps it. Once the session has threads, `use` is a `conflict` (`this session already works with N cloud thread(s) (…) on <source>; start a new omp session to use <source>`). A switch leaves running previews alone. `connect` pairs a cloud you name and, for a session without threads, switches to it (`this session uses it now`); otherwise it says `this session keeps <source>: it already works with threads there`, and when a `url` or `OMP_CLOUD_URL` is set it adds `new sessions use … first`. Declining the dialog is `forbidden` and writes nothing; an existing pairing is a `conflict` (`cloud use {cloud: "paired"} uses it; replacing a pairing is your /cloud connect --replace`).

## What info says about agents

After the models, `info` reports what a cloud agent may do and what happens to its work, from the service's settings (a device token may read them) and `whoami`:

- `agents may: fetch yes|no · web search yes|no · browser yes|no · egress open|N destinations`, plus `· read-only` when the service sets `policy.readOnly`. A delegation's policy can only tighten these.
- `agent toolchain: <vm.packages>` (Debian with git, curl, jq and sudo).
- `agent results: <push mode> · pull requests <git.pr> after a push to a github.com repository with the GitHub App · signing <git.sign> · push credentials for <hosts>`, with the push mode one of `kept for the user to pull (git.push never)`, `pushed when the user approves each push (git.push ask)` and `pushed after every turn (git.push auto)`.
- `plan mode: on: …` only while omp is in plan mode.

When the settings cannot be read, one `agents: not reported (<code>)` line replaces the first three.

## Native views

In Tern the tool's calls and results draw natively instead of as text: `wait` and `status` as job tiles under omp's own wait head (`waiting on N of M jobs`, `M jobs settled`, counts of done, failed and cancelled), `list` as tiles in a section per repository, and the other ops as key-value, text, code and diff blocks. A call's partial view is replaced by its result view. A terminal UI and the model see the text result.

## Scratch threads

`/cloud` hands off the repository you are in. For work that needs none, such as research, a review of a pasted document or a scratch script, the model delegates with `workspace: "scratch"` (the default outside a git repository, or in one without a commit): the cloud agent starts in an empty repository, nothing of your machine's files is shipped, and its result is an ordinary branch. `/cloud pull <id> --into <dir>` (or `pull` with `into`) clones it into a new directory.
