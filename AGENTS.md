# Agent guide for omp-cloud

Self-hosted cloud agents for omp on vibemon (`vmon`) microVMs. `docs/*.md` and `CHANGELOG.md` are the reference and change in the same commit as the code: design reasons and known limitations go in `docs/architecture.md`, the contract in `docs/api.md`, trust boundaries in `docs/security.md`. Verified facts about omp, vmon and the rest of the stack that the code relies on are in this file or in the comment of the code that depends on them. Owner-specific host notes go in the untracked `AGENTS.local.md`. Read `docs/architecture.md` first.

## Stack and commands

- TypeScript on Bun 1.4.3, managed by mise, which also pins shellcheck 0.11.0: `test/install-sh.test.ts` checks `install.sh` with it and skips where it is missing, so run tests through mise (`mise run test`). CI (`.github/workflows/ci.yml`) typechecks and runs `bun test` with Bun 1.4.3.
- Dependencies are exact versions in `package.json`; the `@oh-my-pi/*` packages move together.
  - `@oh-my-pi/pi-ai` is imported directly by the login flow (`src/auth/login.ts`), `@oh-my-pi/pi-tui` by the plugin's job tiles (`tools/job-widget`), `e2b` is the SDK that talks to vmon.
  - `reflect-metadata` must be evaluated before `@peculiar/x509`: `src/setup/tls.ts` generates setup's TLS identity in-process and imports both there in order.
  - `react`, `react-dom`, `lucide-react` and `@types/react*` are the dashboard client; `puppeteer-core` is for the showcase capture scripts (`scripts/showcase/`).
  - vibemon is pinned in `infra/vmon.json`.
- omp itself is not pinned for the service host and the VMs: they follow the owner's omp, Tern's managed install when it exists (`hostOmp()` in `src/omp-version.ts`), else the first `omp` on PATH. `omp-cloud setup` resolves the broker and gateway binary the same way (`findOmp()` in `src/setup/context.ts`, which also looks in `~/.local/bin`) and installs omp with omp's own installer when there is none. CI installs the omp version `package.json` pins for `@oh-my-pi/pi-coding-agent` (`.github/actions/install-omp`), because some unit tests run `omp session pack`. VM templates get omp from omp's build service (`src/vmon/template.ts`).
- The plugin's omp minimum is `MIN_OMP_VERSION` in `plugin/src/index.ts`; [Install](docs/install.md#requirements) states it for users, so change both. `plugin/src/index.ts` is a thin async entry with no runtime imports but `node:` built-ins: it lazily imports `./main` (the entry body, exporting `register(pi)`), and when that fails it registers only a `/cloud` command and a `session_start` notice that name the real error, blaming the omp version only when the omp is older than the minimum. The command's description starts with `LOAD_FAILED_MARKER` (`omp-cloud could not load:`, exported from `index.ts`; never reword it): `src/setup/plugin-probe.ts` recognises a failed load by it, for the `plugin.loads` check of `setup` and `doctor`. Keep new top-level imports of omp host modules in `main.ts` and what it imports, never in `index.ts` (`plugin/test/entry.test.ts`). A literal dynamic `import()` of a served module gets the same module instance as a static one; prefer static imports (`plugin/src/cards.ts` uses a dynamic one on purpose). Cloud agents run as omp background jobs through the host's exported `AsyncJobManager` (`plugin/src/cloud-jobs.ts`), which couples the plugin to omp internals; re-check it when omp's version moves.
- **Runtime imports must be ones a compiled omp serves.** A compiled omp has no `node_modules` for the plugin it loads: it answers `@oh-my-pi/*` imports from a registry built into the binary from the `package.json` exports of seven packages, and for coding-agent (and agent, ai, natives, utils) only the named exports, not the catch-all `./*`. So the plugin and the VM extension must not import coding-agent's `irc/*` or `job-widgets/*` at runtime (`import type` is free; pi-tui's `tools/job-widget` is served). A checkout hides a violation, because the specifier resolves into this repository's `node_modules`. `plugin/test/host-imports.test.ts` is the gate for `plugin/src` and `src/runner/vm-extension/`: it checks every runtime `@oh-my-pi/*` import against the served set derived from the pinned packages and, when Tern's omp binaries are in `~/.local/share/tern/omp/versions`, looks the key up in every binary from the plugin's minimum omp up. Wrap every deep import so a missing member degrades instead of throwing (feature-detect it, as `cloud-agents.ts` and `src/runner/vm-extension/irc-peer.ts` do).
- `omp-cloud` is one binary and a command line. `src/bin.ts` dispatches `serve` (the default), `setup`, `doctor`, `login` and `uninstall` (`src/setup/`), `ssh-pair` (`src/cli.ts`), `update` and `install` (`src/update/`), `backup` (`src/backup.ts`) and `version`; usage and contract are in `docs/api.md`, "The omp-cloud command".
  - `bin.ts` imports each command's module when the command runs, never at the top: the service pulls in omp's SDK, which installs process-wide signal and exit handlers and loads slowly, and `version`, `--help`, `ssh-pair` (over ssh) and `backup` must not pay for that. `src/main.ts` and `src/cli.ts` stay importable for `bun run` in a checkout (`mise run serve`, the wrapper); `scripts/backup.ts` is a thin caller of `src/backup.ts`.
  - In a checkout `mise run infra:up` (`omp-cloud setup --checkout`) writes the wrapper `~/.local/bin/omp-cloud`: a `#!/bin/sh` script with the units' fixed PATH that execs the absolute bun on `src/cli.ts` (`installCheckoutWrapper` in `src/setup/managed.ts`). `uninstall` removes it, or a managed install's link, and leaves any other file there. On a managed install that name is a link to `<app>/bin/omp-cloud`, made by `omp-cloud setup`.
  - `ssh-pair`'s last stdout line is a JSON record, `{"ompCloudPair": 1, …}` or `{"ompCloudPair": 1, "error": …}` with exit status 1, which `plugin/src/ssh.ts` parses: that output is a contract (`docs/api.md`, "SSH pairing"), change both together.
  - **Schema rule:** the CLI opens the database next to the running service with `Store.open({migrate: false})`, which throws `SchemaVersionError` unless `PRAGMA user_version` equals the code's migration count, so it never migrates a database the service owns. A new migration therefore makes the CLI refuse until the service has restarted, and a checkout older than the data says to `git pull`.
- Versions: the root `package.json` `version` is the service's (`src/version.ts` `SERVICE_VERSION`). `API_VERSION` in the same file is an integer that rises when the contract gains something. `whoami` reports both, plus `capabilities` (the list in `src/server/app.ts`: add a name there when you add a feature a client may depend on). The plugin version (`plugin/package.json`) and `.omp-plugin/marketplace.json` must be equal (`plugin/test/manifest.test.ts`); raising it is what makes `omp plugin upgrade` move a marketplace install. Updating a checkout's server is `mise run backup`, `git pull`, `systemctl --user restart omp-cloud` (migrations run at start); a managed install updates itself (the dashboard pill, `/cloud update`, `omp-cloud update apply`).
- Service side of the HTTP contract: `src/server/list.ts` (the paged thread list and its cursors), `query.ts` (integer parameters), `inspect.ts` with `inspect-gate.ts` (diff, tree and files from the stored result bundle through `src/git/inspect.ts`; at most 2 at once), `turn-text.ts` (paged replies) and `model-ids.ts`; scratch threads come from `GitService.scratchSource()`.
- Plugin internals worth knowing:
  - `errors.ts` is the one error type (`CloudError` with `code`, `retriable`, `outcomeKnown`; `api.ts` retries and throws only that).
  - `resolve.ts` resolves thread references through the service; `Cloud.waitFor` is in `verbs.ts` and `wait.ts` decides which states end a wait.
  - `tool.ts` (schema, descriptions, error envelope) with `tool-ops.ts` (the 14 ops) is the `cloud` tool; `launch.ts` is the batch handoff; `ssh.ts` is the only code that runs `ssh`.
  - `plugin/test/helpers.ts` exports `FAST_RETRY`: pass it as `Cloud`'s `tuning` argument in tests that hit an unreachable service, or they wait out the retry backoff.
  - `CloudClient.irc` retries an ambiguous send up to 4 POSTs with one message id (the service dedupes by id); `sendMessage` and the other non-idempotent posts (`applyUpdate`) are never retried.
- Updates and releases (contract in `docs/api.md`, "Updates"):
  - Releases are GitHub Releases of `TechDufus/omp-cloud`; the plugin ships through the omp marketplace. vibemon updates through its official releases (`stencil-hq/vibemon`) but each omp-cloud release pins the vibemon it was tested with, because a vmon upgrade can change the snapshot format and needs root.
  - `src/version.ts`: a release build injects `SERVICE_VERSION` and `BUILD` (`{id, commit, createdAt}`) with `--define` (`__OMP_CLOUD_VERSION__`, `__OMP_CLOUD_BUILD__`); without them (a checkout, tests) the version is `package.json`'s and `BUILD` is `{id: "dev", …}`. Read the defines only through `typeof`.
  - A process is **managed** when `realpath(process.execPath)` is inside `<app>/versions/<version>/` (`managedVersion()` in `src/update/layout.ts`; `<app>` is `OMP_CLOUD_APP_DIR`, default `~/.local/share/omp-cloud/app`); nothing else makes it so. Anything run from a checkout is `unsupported`, and tests set `OMP_CLOUD_APP_DIR` to a temp directory.
  - Updater code is in `src/update/`, its routes in `src/server/update-routes.ts`, the dashboard's side in `src/dashboard/handoff.ts` (sessions across an update restart) and the client's `app/update*.ts(x)`, `app/UpdatePill.tsx` and `pages/UpdateCard.tsx`, the plugin's in `plugin/src/update.ts`. Updater tests go through the `CommandRunner` seam (`src/update/test-support.ts`), never the real systemctl.
  - The vibemon pin is `infra/vmon.json` ([Updating](docs/updating.md#vibemon-is-pinned)): `omp-cloud setup` installs exactly it and `release.json` `requires.vmon.version` is read from it, so raise it only after testing the new vmon. The VM template tag covers the installed vibemon version, so a vibemon upgrade builds a new template. The root helper takes one tag argument and nothing else from its caller. `src/vmon/vmon-install.test.ts` runs it unprivileged against temp directories with its `VMON_INSTALL_*` overrides, which it refuses as root. `scripts/vmon-restart-check.ts` restarts the shared live vmon under a running turn: it needs `OMP_CLOUD_ALLOW_VMON_RESTART=1` and the owner's go, and has no mise task.
  - The compiled binary embeds omp's native addon: `@oh-my-pi/pi-natives` loads a platform `.node` that `bun build --compile` does not carry. `scripts/embed-natives.ts` replaces the SDK's `native/embedded-addon.js` with zstd frames of the addon (x64 embeds `modern` and `baseline`, arm64 `default`, fetched from the npm registry and checked against `dist.integrity`), and `scripts/release.ts` builds through `Bun.build({compile})` for that reason, not the `bun build` CLI.
  - `THIRD-PARTY-NOTICES.txt` (`scripts/notices.ts`): a bundled package with no license text fails the build naming it. Supply the text in `scripts/license-texts/<name>@<version>/`; a version bump of such a package fails until the text is re-checked and the directory renamed.
  - `mise run release -- <version>` needs a clean tree, bumps `package.json`, `plugin/package.json` and `.omp-plugin/marketplace.json` together, moves `## Unreleased` into the version's section, and commits `release: <version>` and tags `v<version>` locally. It pushes nothing; pushing (`git push origin HEAD v<version>`) starts `.github/workflows/release.yml`, which needs the owner's go.
- One-command install (`omp-cloud setup`, `docs/install.md`):
  - `install.sh` (repository root) is POSIX `sh`, never uses sudo and never edits an rc file: it downloads `omp-cloud-linux-x86_64` and its `.sha256` sidecar, verifies, and runs `omp-cloud setup "$@"` (`OMP_CLOUD_VERSION`, `OMP_CLOUD_DOWNLOAD_URL`). `test/install-sh.test.ts` runs the real script against a local static server. Keep it POSIX (no bashisms).
  - Setup splits root from user. The user process plans, asks once, then runs one `sudo -- <self> setup system …` for all root work (packages, the vibemon helper and its sudoers rule, vibemon at the pin, `/etc/vmon/env`, the persistent system units `omp-cloud-net` and `vmon`, the vibemon team, linger); `src/setup/system.ts` refuses to run unless it is root. Everything else (config, TLS, units, plugin, login) runs as the user. Never add a second sudo.
  - Every step reports `{id, status, detail, fix}` through `Reporter` (`src/setup/steps.ts`). Setup, `doctor` and `uninstall` take everything they touch outside their own code (the command runner, environment, paths, preflight and health probes, prompts, the omp lookup, the plugin, login and system-check parts) from a `SetupContext` (`src/setup/context.ts`) that tests replace with fakes in a temp directory: no test under `src/setup/` runs a root command or touches a live unit, and a new probe belongs in the context, not in a direct call. Run them with `bun test src/setup`.
  - The binary embeds the plugin; setup extracts it to `<app>/marketplace/<v>/` and installs it with `omp plugin`; a linked plugin (checkout mode) is left alone. The updater's non-fatal `plugin` step refreshes it after an update (`src/update/real.ts`).
- Cloud agents as omp agents (`docs/jobs.md`; the IRC endpoint is in `docs/api.md`):
  - Plugin: `cloud-agents.ts` makes each followed thread an `AgentRegistry` ref (`kind: "sub"`, id = the job id) with a `CloudSession` shim, so omp's own `agent://`, `history://`, `proc://`, `write agent://<id>` and wait paths work. `cloud-jobs.ts` registers the running turn as an `AsyncJobManager` task job: a model-started thread's result is omp's `async-result` (the `[cloud]` card is for user-started threads, never both). A user's cancel stops the cloud turn, while omp's own cleanup (`/clear`, a new session, switch, fork, branch, `/btw`) does not: omp cancels the session's jobs on all of them with the same abort reason, so the plugin treats a cancel as cleanup when the main agent's `AgentSession.isSessionTransitioning` is true, or on the manager's shutdown reason, or inside a 5 s switch window for an omp without the getter. `job-widgets.ts` wraps `manager.widgets` because omp has no extension API for job widgets. A `rows` node from omp-cloud is a regression (`mise run parity:capture -- --assert`).
  - Service and VM: `src/runner/irc.ts` and `thread.ts` deliver a message into a running turn as an RPC `prompt` of `/irc-in <json>` and make an idle thread's message an `irc` turn. `src/runner/vm-extension/irc-peer.ts` is the VM side: `provisionVm` uploads it with `~/.omp-cloud/irc.json` and `ompLaunchArgs` loads it with `-e`; it imports nothing from the repository, and the compiled-omp import limit above applies to it.
  - To see what omp sends to the terminal, run omp with `OMP_TUI_DEBUG=<socket>`.
- Every command is a mise task (`mise tasks`):
  - `serve`, `test`, `typecheck`, `smoke`, `scenario`, `plugin:scenario`, `template`
  - `infra:up` and `infra:down` (`omp-cloud setup --checkout` and `omp-cloud uninstall --checkout`: the dev-mode install of this checkout; `mise run infra:up -- --no-login --yes …` passes flags through; they ask for sudo once)
  - `install:scenario` (`test/install-scenario.ts`: builds the x64 release, serves it with `install.sh` to a clean Debian 13 VM in the vmon team `omp-cloud-test`, runs `curl | sh`, checks `doctor`, units, linger, a real turn in a nested VM, a rerun and `uninstall --purge`; slow; `-- --no-nested` for a host whose nested KVM kills the VM) and `cleanhost -- create|exec|put|get|destroy|list|template|nested` (`scripts/cleanhost.ts`, `test/cleanhost/vmon.ts`: those clean VMs by hand; key `~/.config/omp-cloud/vmon-test.key`; a VM is killed after 3 hours, or 24 with `create --keep`; destroy what you create)
  - `dashboard:dev` (`scripts/dashboard-dev.ts`: the dashboard on invented data in a temp directory, runner off, with a one-time sign-in link; Ctrl+C removes everything; `--update=<state>` scripts the update card; `--showcase` seeds `scripts/showcase/profile.ts` and runs the service through `scripts/showcase/service.ts` for the captures; `docs/assets/src/` is gitignored and `scripts/showcase/optimize.ts` turns the raw captures there into `docs/assets/`)
  - `backup` (`scripts/backup.ts` runs `src/backup.ts`, which is also `omp-cloud backup`; behaviour and flags in [Backups](docs/operations.md)). Setup installs the daily `omp-cloud-backup.timer` beside the user units.
  - `site:build` and `site:dev` (`site/build.ts`, `site/dev.ts`: the website, details in [Development](docs/development.md))
  - `release:build` (`scripts/release.ts build`: `dist/`, gitignored, holds `omp-cloud-linux-x86_64` and `omp-cloud-linux-arm64` compiled from `src/bin.ts`, a `.sha256` sidecar for each, `release.json`, `notes.md` and `THIRD-PARTY-NOTICES.txt` with its sidecar; `-- --version X`, `-- --out dir`) and `release` (`mise run release -- <version>`, above)
  - `update:scenario` (`test/update-scenario.ts`: builds real releases, makes one a managed install under a throwaway user unit `omp-cloud-e2e-*` with a temp app directory and a static feed, updates it, rolls a release that fails its health check back, and checks that a checkout is `unsupported` and that the live units did not change; needs a systemd user manager, the pinned vibemon, an omp and the network, takes minutes, uses no VM or model)
  - `parity:capture` (`scripts/parity/`: the native-parity harness, a scripted session on a real omp with the plugin, the fake model and a throwaway service on the local vmon, once through a pty that speaks Tern's protocol and once in tmux with `PI_TUI_NATIVE=0`; flags and behaviour in `docs/development.md`). It shares the local vmon and the gateway clients file with `scenario`, `plugin:scenario`, `update:scenario` and `install:scenario`, so all five take one run lock (`test/run-lock.ts`): a second run refuses to start and names the holder (exit 2). `parity:capture --no-cloud` takes no lock.
  - `dev:local`, `dev:provider`, `dev:play` (`dev/local.ts`, `test/fake-provider.ts`, `dev/play.ts`: developer tools, not acceptance scenarios; `dev/env.ts` reads `~/.config/omp-cloud/vmon.key`)
- `test` runs `bun test` and `typecheck` runs `bunx tsc --noEmit`, then `bunx tsc --noEmit -p src/dashboard/client` (the dashboard client has its own tsconfig with the DOM lib; the root one excludes it). `smoke` curls the API of a fresh service in a temp directory with the runner off; it needs no VM. `scenario` drives the API end to end on local vmon with the fake provider (`test/fake-provider.ts`; its git steps serve a bare remote with `test/git-http.ts`). `plugin:scenario` installs the plugin the way users get it (`docs/development.md`). `template [version]` builds the vmon template `omp-agent:<version>-<recipe hash>` by hand; the runner also builds a missing tag on first use, so a change to the recipe (`agentTemplate` in `src/vmon/template.ts`) reaches new VMs by itself.
- The service lives in `src/`: `server/` (HTTP), `store/` (SQLite and blobs), `runner/` (VMs and omp; `runner/vm-extension/` is the code uploaded into each VM), `settings/` (the run-time settings registry and store, and `tighten.ts`, which lays a thread's own policy over the service's), `git/` (the service-side git cache, base fetches and pushes), `dashboard/` (the dashboard listener and its web client), `pairing/` (remote-listener identity, pairing codes, allowed sources), `vmon/`, `gateway/`, `auth/` (the `/cloud login` flow), `config.ts` and `main.ts`. The API, dashboard and remote listeners are defined in [API](docs/api.md#listeners).
  - `service.json` holds bootstrap only (listen addresses, paths, vmon, gateway, broker, git hosts with credential commands, dashboard, remote); `listen` is plain HTTP and must be loopback, other machines use the `remote` TLS listener with paired devices. Run-time settings and policy (`git.push`, `policy.*`) live in the database and change through `/api/v1/settings`, never by editing `service.json`; a thread may tighten that policy through the create request's `policy`, never loosen it. Its HTTP contract is `docs/api.md`; change both together.
  - `plugin/` is the `/cloud` plugin, a standalone package with its own `guards.ts`. Its settings (`url`, `token`, `excludeExtensions`, `secretFiles`, `secretEnv`, `policy`, `deliver`) live in omp-cloud's own files, `~/.config/omp-cloud/config.yml` (`$XDG_CONFIG_HOME`, `%APPDATA%` on Windows) and a repository's `.omp-cloud.yml` (`plugin/src/config.ts`): omp-cloud never writes to omp's config or registers anything in omp's settings registry, because it is a separate project that only installs as an omp plugin. `deliver` (`tray`, the default, or `transcript`) is personal-file only. A paired device's connection (pinned certificate and device token) is `connection.json` next to that file.
- The dashboard client in `src/dashboard/client/` is React 19 on the vendored omp-stats UI kit in `kit/` (MIT): edit `pages/` and `app/`, not the kit. `api.ts` and `live.ts` stay framework-free. It has its own tsconfig (DOM lib, `jsx: react-jsx`) and a dev loop in `mise run dashboard:dev`.
- The website in `site/` (own tsconfig, DOM lib) is a static Bun + React build that renders `docs/*.md`, `CHANGELOG.md` and named `README.md` sections with `Bun.markdown` (its heading ids match GitHub's), styled by importing the kit's CSS (never its TSX). A new `docs/*.md` must be added to `NAV` in `site/nav.ts`, and renaming a README section the landing reads (`site/pages/Landing.tsx`) fails the build. `site/client/` is plain DOM code that imports only `site/config.ts`. Every URL it emits is page-relative, so the site works at a domain root and under a subpath. `.github/workflows/pages.yml` deploys `main`; it is skipped while the repository is private.

## Service host (`omp-cloud setup`)

- `omp-cloud setup` (code in `src/setup/`; `infra/vmon-install.sh` and `infra/vmon.json` stay in `infra/`) installs the service host, `--checkout` for this repository (units run `bun run src/main.ts`, the plugin is linked from `<repo>/plugin`, no managed install) and without it from a release binary. `omp-cloud doctor` checks it and `omp-cloud uninstall` removes it. User units and system units are persistent.
- vmon runs as the system unit `vmon`, with its API on `127.0.0.1:3000`; setup's one `sudo` installs it at the pin in `/opt/vmon`, with `/etc/vmon/env` written once with random secrets, its net pool (default `172.20.0.0/16`, else the first free of `172.29`, `172.30`, `172.31`; kept on reruns) and `KillMode=process`, so a restart of the unit keeps the VMs. The vibemon team is `omp-cloud` (`--team`), with its limits set on every run (`--max-sandboxes`, default 32). vibemon cannot delete or rename teams (stencil-hq/vibemon#6).
- The updater moves vibemon through the root helper `/usr/local/libexec/omp-cloud/vmon-install` (a root-owned copy of `infra/vmon-install.sh`, embedded in the binary) under the sudoers rule `/etc/sudoers.d/omp-cloud`, validated with `visudo -cf` ([Updating](docs/updating.md#vibemon-is-pinned), [Security](docs/security.md#what-runs-as-root)). Change the pin and the script in the repository, never the installed files by hand. `uninstall` removes the helper and the rule; `--purge` also `/opt/vmon`, `/opt/vmon.prev`, `/etc/vmon`, `/var/lib/vmon` and `/etc/omp-cloud`.
- Service IP `10.254.254.1` (dummy link `ompsvc0`, the system unit `omp-cloud-net`) is the only host IP the VMs can reach.
- Any host listener bound to `0.0.0.0` is reachable from every VM, because vmon's egress proxy dials from the host and its exemption covers every port of the gateway address (`10.254.254.1`): a new host service must bind loopback or a specific address, or refuse that source (the remote listener does; [Security](docs/security.md)).
- The omp auth broker (`127.0.0.1:8765`) and gateway (`10.254.254.1:4000`) run as the user units `omp-auth-broker` and `omp-auth-gateway`; the gateway unit's `ExecStartPre` waits up to 30 s for the broker's token. `omp-cloud login` drives the service's own `/api/v1/logins` flow with `service.token`.
- Every user unit runs with one fixed PATH, never the caller's (`unitSearchPath` in `src/setup/units.ts`; [Configuration](docs/configuration.md#service-config)). Anything the service runs must be on it or named by absolute path.
- The service runs as user unit `omp-cloud` (`bun run src/main.ts` in this repo with `--checkout`, else `<app>/bin/omp-cloud serve --config <service.json>`; logs: `journalctl --user -u omp-cloud`), installed and started by `setup`. The API listener is `127.0.0.1:8080` and the dashboard listener `127.0.0.1:8081` (`dashboard.listen`). Restart the unit after changing `src/` (`systemctl --user restart omp-cloud`), and stop it before `mise run serve`, which binds the same addresses. An update's applier runs as the transient unit `omp-cloud-update`.
- The remote listener (`remote` in `service.json`) is TLS on `0.0.0.0:8443` and the one omp-cloud listener off loopback. Setup generates its identity in `~/.config/omp-cloud/tls/` once in-process (`src/setup/tls.ts`) and never regenerates it: replacing it unpairs every device ([Pairing](docs/pairing.md)). `setup` never touches the firewall. Tests and `smoke` give it a temp identity and `allow: ["127.0.0.0/8"]`.
- The gateway clients file (`~/.local/share/omp-cloud/auth-home/clients.json`) is shared by the dev tools and the service. Write it only through `GatewayClients`, which keeps every other entry; `setup` merges its own entry (`--checkout` adds the dev client `omp-cloud-dev` with its token in `~/.config/omp-cloud/gateway-client.token`).

## Secrets

Never print, log or commit them. Load them at runtime; see `dev/env.ts`. Owner-specific host notes (a deployed host's state, exact secret-manager references, launcher layout) live in the untracked `AGENTS.local.md`, when it exists.

| Secret | Location |
|---|---|
| vmon team key | `~/.config/omp-cloud/vmon.key` (0600; the service and the dev tools read it; `setup` checks it against vmon and mints a new one when vmon does not know it) |
| Gateway client token | `~/.config/omp-cloud/gateway-client.token` (checkout mode only); per-thread gateway client tokens live only in their VM's `models.yml`; the service's own client token lives only in its memory |
| Broker token | `~/.local/share/omp-cloud/auth-home/.omp/auth-broker.token`, inside the broker vault; the service reads it to upload `/cloud login` credentials |
| Owner token | `OMP_CLOUD_TOKEN` in the environment, or a password-manager `!command` (for example `!op read …`) as `token:` in omp-cloud's own `~/.config/omp-cloud/config.yml`, which never ships to a VM. `setup` writes `~/.config/omp-cloud/service.token` only when it creates `service.json`, which holds only the SHA-256, and writes `config.yml` only when it is absent, with `token: "!cat <service.token>"`: to keep the token in a password manager, store it there, change `token:` and delete the file |
| TLS private key | `~/.config/omp-cloud/tls/key.pem` (0600, in a 0700 directory; the service refuses to start otherwise). The certificate beside it is public; devices pin its SHA-256 fingerprint |
| Device tokens | `ompd_…`, one per paired device. The service stores only their SHA-256 in the database (`devices` table); the plaintext exists only in that device's `connection.json` (`<config home>/omp-cloud/`, 0600). Pairing codes carry a one-time secret that is stored hashed and expires in 5 minutes |
| vmon secrets | `/etc/vmon/env` (root only): `VMON_CLUSTER_SECRET` and `VMON_ADMIN_TOKEN`. The admin token signs in to vmon's dashboard at `http://127.0.0.1:3000/dashboard/` and its `/admin` API (`X-Admin-Token`) |
| Broker vault | `~/.local/share/omp-cloud/auth-home` |
| Update feed token | The `update.token` setting, empty by default and needed only for a private repository or fork: a `!command` such as `!/usr/bin/gh auth token`, the name of an environment variable of the service, or a literal. A literal is stored in the clear in the database but reads back as `(set)` and is never audited or exported, so prefer the command |

## Rules

- **TypeScript:**
  - No `any`: use `unknown` with guards.
  - No one-line wrapper functions unless the function is a type guard or a real contract.
- **Tests:** VM tests against local vmon are free. Anything that calls the gateway uses a model subscription, so keep those runs short: `dev:play`, or any real provider.
- **Shared state:** ask before pushing, deleting VMs you did not create, changing vmon limits, or touching the broker vault.
- **Changelog:** every user-visible change adds an entry under `## Unreleased` in `CHANGELOG.md` in the same change, written for someone who runs the service; `mise run release` moves it into the version's section, and the release workflow publishes that section as the release notes. Do not edit a released section or the version files by hand.
- **Root helper:** the vibemon helper takes exactly one tag argument and nothing else from its caller. Tests and agents never edit `/etc/sudoers*` or `/opt/vmon`, never run the helper as root and never touch the live `omp-cloud`, `omp-auth-*` or `vmon` units to test an update: use temp app directories and throwaway unit names (`update:scenario`).
- **vmon:** never put secrets in egress header `rules` or in network config (their values come back from `GET /sandboxes/{id}` and sit in plaintext node metadata). Webhooks drop an event after 3 failed attempts, so reconcile by listing sandboxes and never trust webhooks alone. Pause a VM only while omp is idle: output produced while nobody is attached is lost, and omp's session file is the record.
